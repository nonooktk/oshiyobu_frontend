# PR を出す前・main に入れる前の確認

次の表の項目を、上から順に確かめます。結果は、最後に**表**で出します。**1 つでも × があれば、そこで止まり**、次へ進みません（PR を出さない・承認を求めない）。

- 確認の段階は 2 つある。**A: PR を出す前**（項目 1〜8）と、**B: main に入れる前**（項目 1〜8 に、項目 9〜10 を足す）。
- コマンドは、Mac・Linux の bash 用と、Windows の PowerShell 用を並べてある。自分のシェルに合うほうを使う。
- `.env` や `*.env` を開いて中身を読むことは、この確認でもしない。

## 確認項目

### 1. 作業ブランチにいる

```
git branch --show-current
```

`main` ではなく、作業用のブランチ名が出れば ○。

### 2. 差分が、意図したファイルだけ

```
git status --short
git diff --stat main...HEAD
```

変えるつもりのファイルだけが並んでいれば ○。次のものが混ざっていたら ×。

- `.env`・`*.env`・鍵（`*.pem`・`*.key`）
- 依頼されていない `.github/`・`.claude/`・`CLAUDE.md` の変更
- backend の計算・データ・API にあたるファイル
- 大きなファイルや、関係のない画像

### 3. 秘匿値・個人情報が入っていない

差分に、トークン・鍵・パスワード・メールアドレスらしい文字列が無いか探す。

bash:

```
git diff main...HEAD | grep -n -i -E "api[_-]?key|secret|token|passw|private key|ghp_|github_pat_|sk-|AKIA|[A-Za-z0-9._-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}"
```

PowerShell:

```
git diff main...HEAD | Select-String -Pattern 'api[_-]?key|secret|token|passw|private key|ghp_|github_pat_|sk-|AKIA|[A-Za-z0-9._-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}'
```

- 何も出なければ ○。出たら、1 件ずつ中身を確かめる。本物の値や個人のメールアドレスなら ×。画面の文言やコード上の変数名で、秘匿値ではないと言い切れるものは、○にしてよい（理由を表に書く）。
- あわせて、commit の作者のメールアドレスを確かめる。

```
git log main..HEAD --format="%h %an <%ae>"
```

`@users.noreply.github.com` で終わっていれば ○。個人のメールアドレスが出たら ×（直し方は `docs/はじめに.md` の「作者の名前とメールアドレスを決める」）。

### 4. 画面に使わない語が無い

「新しい口座を開く」「口座開設」「確約」が、画面の文言やデモ用のデータに無いか探す。この文書と `CLAUDE.md`・`docs/` は、語そのものを説明のために書いているので、探す範囲から外す。

```
git grep -n -E "新しい口座を開く|口座開設|確約" -- . ':!CLAUDE.md' ':!.claude' ':!docs' ':!.github'
```

（bash と PowerShell で同じコマンドが使える。）何も出なければ ○。出たら ×。口座に触れる言い方は、「今の口座に推しを登録する」「推し活定期」にする。

### 5. 「デモ用の架空データ」の表示が残っている

```
git grep -n "デモ用の架空データ"
```

- 表示のある箇所が出て、main と比べて**減っていなければ** ○。減っていたら ×。
- あわせて、ローカルで**全画面**を開き、どの画面にも表示が出ていることを、目で確かめる。画面を足した場合は、足した画面にも出ていること。

main との比較（箇所の数）:

```
git grep -c "デモ用の架空データ" main
git grep -c "デモ用の架空データ"
```

### 6. テストとビルドが通る

- 実行するコマンドは、`docs/はじめに.md` の「アプリの起動・テスト・ビルド」に書かれたもの。
- 通れば ○。失敗したら ×（エラーを全文貼る）。
- そのコマンドがまだ書かれていないとき（技術スタックの決定前）は、結果を「未設定」と書き、**× と同じく止まる**。統括に確認する。

### 7. 画面を目で確かめた

- ローカルで、変えた画面と、そこから行ける画面を開く。**スマホの幅と PC の幅の両方**で、崩れ・文字の切れ・はみ出しが無いことを確かめる。
- 確かめた画面と、見えたものを、表に書く。

### 8. 承認を得ている

- **A（PR を出す前）**: 作業の計画について、担当者の「OK」「進めてください」「Aで」「同意です」のどれかが出ている。
- **B（main に入れる前）**: 統括の「OK」「進めてください」「Aで」「同意です」のどれかが、PR のコメントか、チャットで出ている。承認の文言を、表に書き写す。
- 出ていなければ ×。承認を、確認を担当する側が推測で補わない。

### 9. CI が緑（B のみ）

```
gh pr checks <PR の番号>
```

すべて pass なら ○。失敗や実行中があれば ×。CI の中身は、設計の確定後に決まる。それまでは「CI 未設定」と書き、**止まって**統括に確認する。

### 10. プレビューで確かめた（B のみ）

- プレビュー環境で、変えた画面と主要な動きを 1 本、目で確かめている。
- プレビューの仕組みと URL は、設計の確定後に決まる（`docs/デプロイ手順.md`）。それまでは「プレビュー未設定」と書き、**止まって**統括に確認する。

## 出力の形

確認が終わったら、次の表を出す。

| # | 確認 | 結果（○ / ×） | 証拠（コマンドの出力の要点・見た画面） |
| --- | --- | --- | --- |
| 1 | 作業ブランチにいる |  |  |
| 2 | 差分が、意図したファイルだけ |  |  |
| 3 | 秘匿値・個人情報が入っていない |  |  |
| 4 | 画面に使わない語が無い |  |  |
| 5 | 「デモ用の架空データ」の表示が残っている |  |  |
| 6 | テストとビルドが通る |  |  |
| 7 | 画面を目で確かめた |  |  |
| 8 | 承認を得ている |  |  |
| 9 | CI が緑（B のみ） |  |  |
| 10 | プレビューで確かめた（B のみ） |  |  |

- **× が 1 つでもあれば止まる。** × の項目、原因、次にやることを、日本語で書く。直したら、最初から確認し直す。
- すべて ○ なら、そう報告する。そのあとの操作（push・PR の作成・承認の依頼）は、担当者の確認を取ってから行う。**main に入れる操作は、この確認の対象でも、Claude Code が行うものでもない**（承認者が GitHub の画面で行う）。
