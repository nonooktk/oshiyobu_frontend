# 運用ルール（ファン向けの画面。新しい流れ）

どこを変えてよいか、作業の進め方、PR の出し方、素材の決まりを書きます。決まりの正本は `docs/守ること.md` です。

## 1. どこを変えてよいか

### 変えてよい所（見た目）

- `src/fan/fan.module.css`・`src/fan/pages/pages.module.css` などの CSS
- `src/fan/components/`・`src/fan/pages/`・`src/fan/layers/` の部品の、見た目と並び
- `src/fan/art/`（絵の対応と、特典の素材の対応 `rewards.ts`）
- `src/fan/text/`（文言。使わない語の決まりの中で）
- `src/assets/img/`・`assets-src/`（絵。変えたら `npm run images`）と、`public/rewards/`（特典の動画）
- 新しいテスト（新しいファイル）

部品を変えるときは、`仕様.md` の 2 節の目印（`data-plan`・`data-act`・`data-plan-tier`・`data-tasks`・`data-task`・`data-layer-body`・`data-reward`）と、ボタンや見出しの名前を残します。テストと発表の通し確認が、これを頼りにしています。

### 先に管理者へ相談する所

- `src/fan/store/` と `src/fan/domain/`（流れと状態。管理者が持つ）。操作を足したいとき、順番や演出の長さを変えたいときは、変える前に相談します。
- ボタンや見出しの名前を変えたいとき（既存のテストが名前で探しているため）。
- 既存のテストの書き換えが要りそうなとき。
- 新しい色・新しい字（書体に無い字）・量の上限に当たったとき。

### 変えない所

- `src/core/`・`core.lock.json`・`.github/`・`public/staticwebapp.config.json`・`docs/守ること.md`・`tests/guard/`・`.claude/settings.json`（設定で、書き込みを止めてあります）
- 事務所向け（`src/office/`）・発表者用（`src/presenter/`）・共通の部品（`src/shared/`）
- 熱量のゲージの位置（8 割のまま）と、札 2 枚

## 2. 作業の流れ

順番は、計画 → 確認 → 実装です。

作業ブランチを切る（切り元は、まとめ先の `feat/fan-flow-v2`）:

```
cd ~/repos/oshiyobu_frontend
git status --short
git fetch origin
git switch -c feature/fan-look --no-track origin/feat/fan-flow-v2
```

手元の検査（PR の前に、必ず）:

```
npm ci
npm run verify
npm run e2e:solo
```

commit と push:

```
git status --short
git add <ファイル名>
git diff --cached --stat
git commit -m "<何を変えたか>"
git push -u origin feature/fan-look
gh pr create --base feat/fan-flow-v2 --web
```

- PR の向き先は `feat/fan-flow-v2` です。`dev`・`main` には向けません。
- `git add -A` と `git add .` は使いません。ファイル名を 1 つずつ指定します。
- `.env`・鍵のファイル・配らない元の動画が入っていないことを、一覧で確かめます（リポジトリは公開です）。
- push してよいのは、自分の作業ブランチだけです。force push と rebase は使いません（G-25）。
- まとめ先が進んだら、`git fetch origin` のあと `git merge origin/feat/fan-flow-v2` で取り込みます。
- 途中でも、Draft の PR を出してもらえれば、早めに見ます。

### 日程

| 日 | やること |
| --- | --- |
| 11/18 まで | 見た目の PR を `feat/fan-flow-v2` へ |
| 11/19 | 検収。通ったら、`dev` と公開中の版へ反映（統括の承認のあと） |
| 11/20 | 発表 |

素材が 11/18 に間に合わないときは、仮の表示のまま PR を出します。素材は、届いたあとに差し込むだけで済みます。

## 3. PR に書くこと

- 何を変えたか（画面ごとに）。変える前と後の画面の絵（幅 390）。
- `npm run verify` と `npm run e2e:solo` の結果。
- `テスト設計.md` の 5 節の、どれを確かめたか。確かめていないものは、そう書く。
- 足した素材と、その出どころ・容量。
- `store/`・`domain/`・既存のテストに触れたときは、その理由と、相談した記録。
- 公開中の画面の URL と合言葉は、書きません（G-22）。

## 4. 素材（画像・動画・背景）を足すときの決まり

- 置けるのは、自作か CC0 のものだけです。統括から渡された素材は、渡されたとおりに使い、出どころを PR に書きます。出どころが分からないものは、置かずに聞きます。
- 絵は WebP（`npm run images`）。動画は、MP4 か WebM を `public/rewards/` に置きます。1 本 4 MB・合計 5 MB まで（G-15）。音は入れません。
- 動画は、外から読み込みません（G-16）。`rewards.ts` に外の URL を書くと、検査で落ちます。
- `<video>` の `muted` と `playsInline` は外しません。
- 素材に、賭け・運・得を連想させる絵（コイン・札束・くじ・スロット）を入れません（G-04）。
- 実在の人物・既存の作品を思わせる絵を入れません。
- 対応の書き方は、`仕様.md` の 4 節です。

## 5. 困ったとき・管理者へ聞くこと

- エラーは、省かずに全文を貼って聞きます。
- どの決まりに当たるか分からないときは、変えずに聞きます。
- 決まりに反する変更を頼まれたとき、Claude Code は、その場では行いません。どの決まり（番号）に当たるかを伝え、管理者に頼む文面の下書きと、代わりにできる見た目の案を出します。

管理者に頼む文面の雛形:

```
管理者（統括）へ。次の変更をしたく、相談です。
- やりたいこと: <何をどう変えたいか。なぜか>
- 当たる決まり: <G-xx と、決まりの名前>
- 触りたい場所: <ファイル名>
- 変えないと困ること: <>
- 代わりに、自分でできること: <>
```

## 6. 注意

- **この作りは、デモ用に限ります**（G-27）。ログインも本人確認も無く、参加の確認は表示だけです。実際の金銭や個人を扱う用途には、そのまま使いません。
- Claude Code は、リポジトリの一番上のフォルダで起動します（拒否の設定が、起動したフォルダを基準に読まれるため）。
- 動作を確かめたのは Mac だけです。Windows で動かないときは、エラーの全文を管理者へ送ります。
- `.env` と `*.env` は、読まない・コミットしない・内容を書き写さない。

## 7. 土台の側に残っていること（管理者が行う）

- いちばん下のプランの名前の確定（いまは仮）。
- 動画が届いたあとの、iPhone の実機での確認。
