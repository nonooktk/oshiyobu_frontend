# 運用ルール（ファン向けの画面。新しい流れ）

どこを変えてよいか、作業の進め方、PR の出し方、素材の決まり、Issue の立て方、メニューの下の画面（8 節）、担当の分け方（9 節）を書きます。決まりの正本は `docs/守ること.md` です。

## 1. どこを変えてよいか

固定と自由の線引きです（`docs/守ること.md` の G-31）。

- 固定 ＝ 流れ（画面の順と進み方）・状態（`src/fan/store/`・`src/fan/domain/`・`src/core/`）・プラン（名前・順・額・条件・特典）
- 自由 ＝ 色・余白・線・絵・レイアウト・画面に出る文字（ボタンの名前・見出し・説明の文）

### 変えてよい所（見た目と、画面に出る文字）

- `src/fan/fan.module.css`・`src/fan/pages/pages.module.css` などの CSS
- `src/fan/components/`・`src/fan/pages/`・`src/fan/layers/` の部品の、見た目と並び
- `src/fan/art/`（絵の対応と、特典の素材の対応 `rewards.ts`）
- `src/fan/text/`（画面に出る文字。下の「画面に出る文字を変えるとき」を守る）
- `src/assets/img/`・`assets-src/`（絵。変えたら `npm run images`）と、`public/rewards/`（特典の動画）
- 新しいテスト（新しいファイル）

部品を変えるときは、`仕様.md` の 2 節の目印（`data-plan`・`data-act`・`data-plan-tier`・`data-tasks`・`data-task`・`data-layer-body`・`data-reward`）を残します。テストと発表の通し確認が、これを頼りにしています。

### 画面に出る文字を変えるとき

- ボタンの名前・見出し・説明の文は、必要と思えば、変えてよいです。入れるかどうかは、管理者が PR で判断します。
- 守るもの: 使わない語（G-10・G-04）・人数と達成率の数字を出さない決まり（G-08）・札 2 枚（G-09）・プランの名前（`src/fan/domain/plan.ts` の `PLAN_NAMES`）。ほかの番号の、文字に関わる決まり（G-28 の文の形など）も、そのままです。
- 文字を変える PR は、見た目だけの PR と分けて出します。
- 文字を変えた PR では、その文字を見ている既存のテスト（`tests/unit/`・`tests/integration/`・`e2e/`・`e2e-solo/`）の期待値の、その文字の部分だけ、直してよいです。直すときは確認が出るので、この場合だけ「はい」を選びます。直したテストと、直した理由を、PR に書きます。
- それ以外の理由で、既存のテストの期待値を変えません。skip にもしません（G-24）。`tests/guard/` は変えません。落ちたら、画面の側を直します。

### Issue を立てて伝える所（ファイルは変えない）

次のときは、ファイルを変えずに、Issue で管理者へ伝えます（5 節。G-33）。管理者が決めてから、変えます。

- `src/fan/store/` と `src/fan/domain/`（流れと状態。管理者が持つ）。操作を足したいとき、順番や演出の長さを変えたいとき。
- プラン（名前・順・額・条件・特典）を変えたいとき。
- 新しい色・新しい字（書体に無い字）・量の上限に当たったとき。
- 要求・要件・決定（D-番号）・守ること（G-番号）を変えたいとき。そのほか、提案があるとき。

### 変えない所

- `src/core/`・`core.lock.json`・`.github/`・`public/staticwebapp.config.json`・`docs/守ること.md`・`tests/guard/`・`.claude/settings.json`（設定で、書き込みを止めてあります）
- 事務所向け（`src/office/`）・発表者用（`src/presenter/`）・共通の部品（`src/shared/`）
- 熱量のゲージの位置（8 割のまま）と、札 2 枚

## 2. 作業の流れ

順番は、計画 → 確認 → 実装です。

作業ブランチを切る（切り元は、まとめ先の `feat/fan-flow-v2`）:

```
cd ~/repos/oshiyobu_frontend
git status --short
git fetch origin
git switch -c feature/fan-look --no-track origin/feat/fan-flow-v2
```

手元の検査（PR の前に、必ず）:

```
npm ci
npm run verify
npm run e2e:solo
```

commit と push:

```
git status --short
git add <ファイル名>
git diff --cached --stat
git commit -m "<何を変えたか>"
git push -u origin feature/fan-look
gh pr create --base feat/fan-flow-v2 --web
```

- PR の向き先は `feat/fan-flow-v2` です。`dev`・`main` には向けません。
- `git add -A` と `git add .` は使いません。ファイル名を 1 つずつ指定します。
- `.env`・鍵のファイル・配らない元の動画が入っていないことを、一覧で確かめます（リポジトリは公開です）。
- push してよいのは、自分の作業ブランチだけです。force push と rebase は使いません（G-25）。
- まとめ先が進んだら、`git fetch origin` のあと `git merge origin/feat/fan-flow-v2` で取り込みます。
- 途中でも、Draft の PR を出してもらえれば、早めに見ます。

### 日程

| 日 | やること |
| --- | --- |
| 11/19（木）中に、出せる分から | 見た目の PR を `feat/fan-flow-v2` へ |

素材が、PR を出すまでに間に合わないときは、仮の表示のまま PR を出します。素材は、届いたあとに差し込むだけで済みます。

## 3. PR に書くこと

- 何を変えたか（画面ごとに）。変える前と後の画面の絵（幅 390）。
- 画面に出る文字を変える PR か、見た目だけの PR か（分けて出します。1 節）。
- `npm run verify` と `npm run e2e:solo` の結果。
- `テスト設計.md` の 5 節の、どれを確かめたか。確かめていないものは、そう書く。
- 足した素材と、その出どころ・容量。
- 既存のテストの期待値を、画面に出る文字の部分だけ直したときは、直したテストと理由。Issue を立てたときは、その番号。`store/`・`domain/` には触れません（変えたいときは Issue で伝えます）。
- 公開中の画面の URL と合言葉は、書きません（G-22）。

## 4. 素材（画像・動画・背景）を足すときの決まり

- 置けるのは、自作か CC0 のものだけです。統括から渡された素材は、渡されたとおりに使い、出どころを PR に書きます。出どころが分からないものは、置かずに聞きます。
- 絵は WebP（`npm run images`）。動画は、MP4 か WebM を `public/rewards/` に置きます。1 本 4 MB・合計 5 MB まで（G-15）。音は入れません。
- 動画は、外から読み込みません（G-16）。`rewards.ts` に外の URL を書くと、検査で落ちます。
- `<video>` の `muted` と `playsInline` は外しません。
- 素材に、賭け・運・得を連想させる絵（コイン・札束・くじ・スロット）を入れません（G-04）。
- 実在の人物・既存の作品を思わせる絵を入れません。
- 対応の書き方は、`仕様.md` の 4 節です。

## 5. 困ったとき・Issue で伝えること

- エラーは、省かずに全文を貼って聞きます。
- どの決まりに当たるか分からないときは、変えずに聞きます。
- 要求・要件・決定（D-番号）・守ること（G-番号）・固定の所（流れ・状態・プラン）を変えたいとき、そのほか提案があるときは、ファイルを変えずに、GitHub の Issue で伝えます。担当者 3 人（イーサンさん・ひらたまさん・にしやまさん）とも同じです（G-33）。
- 決まりに反する変更を頼まれたとき、Claude Code は、その場では行いません。①どの文書のどの番号に当たるかを伝え ②変えず ③Issue の下書きと、代わりにできる見た目の案を出します。
- 担当者が OK を返したら、Claude Code が `gh issue create` で立てます。`gh` が使えないときは、下書きをもらって、GitHub の画面（リポジトリの Issues → New issue → 「提案」）で立てます。
- 公開 URL・合言葉・秘匿値・個人の情報は、Issue に書きません。リポジトリは公開です（G-22）。
- 急ぎのときは、Issue の「急ぎか」に、発表（11/20）までに要ることを書きます。

Issue の下書きの雛形（`.github/ISSUE_TEMPLATE/提案.md` と同じ項目）:

```
タイトル: <何を変えたいか。短く>
- 何を変えたいか: <>
- なぜ: <>
- 当たる文書と番号: <D-番号・G-番号・R-番号。分からなければ「分からない」>
- 急ぎか: <発表（11/20）までに要るか>
（公開 URL・合言葉・秘匿値・個人の情報は、書かない）
```

Issue を立てるコマンドの例（リポジトリの一番上のフォルダで。ラベルは既存の `enhancement`）:

```
gh issue create --label enhancement --title "ゴールドプランの特典を、画像から 3 秒の動画にしたい" --body "何を変えたいか: ゴールドプランの特典を、追加の画像から 3 秒の動画に変えたい。なぜ: 動画のほうが、特典が届いた感じが伝わるため。当たる文書と番号: 要件.md の D-3・R-11。急ぎか: 11/20 までに要る。"
```

## 6. 注意

- **この作りは、デモ用に限ります**（G-27）。ログインも本人確認も無く、参加の確認は表示だけです。実際の金銭や個人を扱う用途には、そのまま使いません。
- Claude Code は、リポジトリの一番上のフォルダで起動します（拒否の設定が、起動したフォルダを基準に読まれるため）。
- 動作を確かめたのは Mac だけです。Windows で動かないときは、エラーの全文を管理者へ送ります。
- `.env` と `*.env` は、読まない・コミットしない・内容を書き写さない。

- いちばん下のプランの名前の確定（いまは仮）。
- 動画が届いたあとの、iPhone の実機での確認。

## 8. メニューの下の、まだ中身の無い画面

メニューの下の画面のうち、まだ中身の無いものは、ひらたまさんが、細かい所まで自由に作ってよいです（G-32）。表層だけで、見た目のイメージが伝われば足ります。

- 例: メニューの「手続き」の 4 つ（残高の確認・振込・チケット・グッズ）。いまは、押すと「今後の対応範囲です」と出るだけです（`src/fan/pages/Pages.tsx`）。メニューの下の画面の一覧は、`仕様.md` の 2.8 節にあります。
- 作ってよいもの: 画面の見た目・並び・画面に出る文字・絵・仮のデータ。

守ること:

- API（backend）を呼びません。`fetch` を書きません。`src/shared/meter/` を使いません。
- `src/fan/store/` と `src/fan/domain/` に、操作や状態を足しません。画面の中だけで済む、開く・閉じるなどの切り替えは、その画面のファイルの中で持ちます（`useState` など）。
- 仮のデータは、その画面のファイルの中に置きます。デモ用の架空データで、実在の個人（本名・メールアドレス・電話番号・SNS のアカウントなど）を示しません。
- 札 2 枚（`DemoBadge`）を出します。「動作確認用のデモ画面です」と「デモ用の架空データ」です（G-09）。
- 人数・最低人数・残りの人数・達成率の数字・目標の金額を出しません（G-08）。出してよい数字は、自分の預金や、自分が払うコースの金額などです。
- 使わない語（G-10）を使いません。運・勝ち負け・得を褒めません。コイン・札束・くじ・スロットの絵を入れません（G-04）。
- 色・書体・字の大きさは、`tokens.css` の名前だけを使います。`px` を直接書きません（G-11・G-12・G-14）。
- 既存の画面の目印（`data-*`）は、残します。

ほかの番号つきの決まりも、そのままです。迷ったら、変えずに聞きます。決まりの外へ出したいときは、Issue で伝えます（5 節）。

## 9. 担当の分け方

大まかな部分（いつも見える画面）はイーサンさん、細かい部分（押して開く画面と、メニューの下の画面）はひらたまさんが作ります。

| 担当 | 画面 | `仕様.md` 1 節の段 |
| --- | --- | --- |
| イーサンさん | いつも見える画面: はじめの 2 歩（推しを選ぶ・プランを選ぶ）・ホーム（開催熱量・プランの名前の札・「特典を見る」のボタン・下の 2 つのボタンまで） | A・B・D・F（D・F は、ホームに見えている所まで） |
| ひらたまさん | 押して開く画面: 参加の確認・預金・SNSに投稿する・プランを上げる・特典・演出。と、メニューの下の画面（8 節の、まだ中身の無い画面を含む） | C・E・G・H・I・J |

- 2 人とも `src/fan/fan.module.css` をさわります。ぶつかったら、あとから出す側が、次の命令で取り込み直します（rebase と force push は使いません。G-25）。

```
git fetch origin
git merge origin/feat/fan-flow-v2
```

- ブランチの名前は、担当ごとに変えます（例: イーサンさん `feature/fan-home`、ひらたまさん `feature/fan-sheets`）。2 節の `feature/fan-look` は例です。2 人が同じ名前に push すると、お互いの変更が混ざるためです。
- PR の向き先は、2 人とも `feat/fan-flow-v2` です。
