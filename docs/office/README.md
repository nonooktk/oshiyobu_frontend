# docs/office/（事務所向けの画面を引き継ぐ人へ）

この階層は、OSHIYOBU の事務所向けの画面（toB。ブラウザで開く `/`。コードは `src/office/`）を、フロントの担当者が引き継いで作るための文書です。読むのは、担当者本人と、担当者の Claude Code です。

事務所向けの画面は、アーティスト事務所との商談で、営業が相手に見せながら提案するダッシュボードです。ファン向け（`/fan/`）と発表者用（`/presenter/`）は、この階層の対象ではありません。

- 状態: 案（2026-11-14）。管理者（統括）の確認が済んでいないことは、`要件.md` の末尾「確認事項」に残してあります。
- 発表は 2026-11-20 です。

## 文書は 4 つ

| 文書 | 答える問い | 読む目安 |
| --- | --- | --- |
| [要求.md](要求.md) | 誰が、どの場面で、何のために使うか。事業の側の言葉（Slack の原文） | 5 分 |
| [要件.md](要件.md) | 何ができればよいか。いまの画面との差。11/20 までの優先。受け入れの確かめ方。末尾に、統括へ聞くこと | 10 分 |
| [仕様.md](仕様.md) | 1 つの画面をどう割るか。4 象限の見せ方。データの形。部品の残す・直す・足す | 10 分 |
| [運用ルール.md](運用ルール.md) | どこを変えてよいか。作業の流れ。PR。データを足すときの決まり | 7 分 |

仕様は「案」です。細部は担当者が決めてかまいません。変えてはいけないのは、`docs/守ること.md` の番号つきの決まり（G-01 から）と、`運用ルール.md` の「変えない所」です。

## 読む順

1. `CLAUDE.md` の「0. 守ること」（Claude Code は自動で読みます。担当者も 1 回読んでください）
2. この README
3. `要求.md` → `要件.md` → `仕様.md` → `運用ルール.md`

`docs/守ること.md` は、作業を始めるたびに要点が自動で出ます。全文は、`運用ルール.md` で番号を引いたときに開きます。

## 番号について

| 番号 | 意味 | 正本 |
| --- | --- | --- |
| Q-01〜 | 要求。事業の側の言葉を 1 つずつに分けたもの | `要求.md` |
| R-01〜 | 要件。「〜できる」の形 | `要件.md` |
| S-1〜 | 画面の要件 | `要件.md` の 4 節 |
| V-01〜 | 受け入れの確かめ方 | `要件.md` の 7 節 |
| 確認 1〜 | 統括が答えること | `要件.md` の末尾 |
| G-01〜 | 守ること（変えない決まり） | `docs/守ること.md` |

`src/` のコメントにある D-xx・SP-xx・F-xx は、管理者の側の上流文書の番号です。担当者は読めなくてかまいません。必要なときは、管理者に聞きます。

## 最初にやること

道具（Git・Node.js・GitHub の認証・Claude Code）が入っていなければ、先に `docs/はじめに.md` の A（Mac）または B（Windows）を終えます。

Mac:

```
mkdir -p ~/repos
cd ~/repos
git clone https://github.com/nonooktk/oshiyobu_frontend.git
cd oshiyobu_frontend
git fetch origin
git switch dev
npm ci
npm run accept -- --local-api
```

Windows（PowerShell）:

```
New-Item -ItemType Directory -Force -Path "$HOME\repos"
Set-Location "$HOME\repos"
git clone https://github.com/nonooktk/oshiyobu_frontend.git
Set-Location oshiyobu_frontend
git fetch origin
git switch dev
npm ci
npm run accept -- --local-api
```

- `git switch dev` は、この階層（`docs/office/`）が dev にあるためです。dev に無いときは、管理者に聞きます（まだマージされていない可能性があります）。
- `npm run accept -- --local-api` は、手元で API を立てて、検査から画面の通信まで順に確かめます。初回は 1〜2 分かかります。Google Chrome が要ります。
- 最後の行が `判定: 合格` で終われば、準備ができています（括弧の中の数は、検査が増えると変わります）。`未完了` や `不合格` が出たら、**出力を全文**コピーして管理者に送ります。`未完了` を合格として扱いません。
- Node.js は 22 LTS の 22.22.2 以降（24 LTS の 24.15.0 以降、26 以降でも動く）です。奇数の版（23・25）は対象外です。

## Claude Code を始める

リポジトリの一番上のフォルダで起動します（拒否の設定が、起動したフォルダを基準に読まれるため）。

```
cd ~/repos/oshiyobu_frontend
claude
```

起動したら、`/permissions` を打って、拒否の一覧が出ることを確かめます（`docs/はじめに.md` の A-8）。

作業の始めは `/start-task` です。ただし、いまの `/start-task` は「最新の main を取る」手順なので、**main を dev に読み替えます**（確認 3 で、管理者に確かめます）。

## Claude Code への頼み方の例

順番は **計画 → 確認 → 実装** です。計画に「OK」と返すまで、Claude Code はファイルを変えません（`CLAUDE.md` の 1 節）。

1. 読ませる:
   「`docs/office/` の README・要求・要件・仕様・運用ルールを読んで、内容を 5 行で言い直してください。まだファイルは変えないでください。」
2. 計画を出させる:
   「要件の R-11（4 象限を大きく見せる）と R-12（境目を動かす）から始めたいです。触るファイル・当たりそうな決まり（G-xx）・確かめ方を、表にして計画を出してください。OK を出すまで変えないでください。」
3. 実装させる:
   「OK です。計画の 1 番目だけ実装して、`npm run verify` を実行して、結果を見せてください。」
4. データを足す:
   「このデータを `src/office/data/` に足したいです。出典の URL と確認日が揃っているか、個人の情報が入っていないかを、先に確かめてください。」
5. テストが落ちたとき:
   「`npm run verify` が落ちました。テストの期待値は変えずに、原因を調べてください。落ちた出力は全文あります。」

## 困ったとき

- エラーは、全文を貼って聞きます。
- 決まりに当たるか分からないときは、**変えずに**聞きます。
- 聞き方の雛形は、`運用ルール.md` の「6. 困ったとき」にあります。
