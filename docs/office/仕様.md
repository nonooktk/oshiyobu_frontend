# 仕様（事務所向けの画面。大まかな案）

`要件.md` の R-xx を、どんな画面にするかの案です。細部は、担当者が決めます。

- 状態: 案（2026-11-14）。「案」と書いた所は、担当者が変えてかまいません。変えてはいけないのは、7 節の決まりです。
- 4 象限の境目の数え方（3.4 節）と、スクロールの基準（6 節）は、統括の確認待ちです（`要件.md` の確認 1・確認 2）。
- 計算（損益・判定・需要）は、`src/core/` の値を使います。画面の側で式を書きません（`src/office/README.md`）。

## 1. 画面の配置

### 1.1 いまの配置

縦 1 列です。「上の帯 → 推し 5 組 →（地図 | 会場の候補）→ 判定（開催条件・満たせるか | 4 象限）」の順です。地図が高く、判定は 937 px から始まるので、画面の高さ 800 px では見えません（`要件.md` 3 節の測った事実）。

### 1.2 案を 2 つ

どちらも、幅 1280 px 以上が基準です。上の帯と、その下の「条件の帯」（推し 5 組・② 集まる人数・選んでいる市と会場）は共通です。

**案 A: 左から右へ流れる 3 列**

```
┌──────────────┬──────────────┬──────────────┐
│ ①② 地図・順位   │ ③④ 会場の候補   │ ⑤⑥ 損益の要約   │
│    集まる人数    │    過去の公演    │    確度・4 象限  │
└──────────────┴──────────────┴──────────────┘
```

**案 B: 左で選び、右で結果を見る 2 列**

```
┌─────────────────────┬─────────────────────┐
│ 左（選ぶ）            │ 右（結果を見る）        │
│ ① 需要の地図と市の順位  │ ⑥ 確度（札・横棒・4 象限・境目）│
│ ③ 会場の候補           │ ⑤ 損益の要約            │
│                      │ ④ 過去の公演            │
└─────────────────────┴─────────────────────┘
```

案 B は、右の列の並びが、番号の順（①→⑥）と違います。商談の流れを「左で選ぶ → 右で結論を見る」と考えて、統括が強くしたい⑥を右の最上段に置きました。区画の見出しには ①〜⑥ の番号を付けて、話す順を示します。

1. 条件を変えて「どこが変わったか」を見る目の動きが、左（操作）から右（結果）へ 1 本に決まる（Q-12）。
2. ⑥に、幅の半分を使える（統括の優先。決定 3）。

気になる点は、左の列の高さです。地図の高さを 400〜450 px に抑える案です。800 px に収まるかは、作って測ります。

| 境目を動かす | ⑥の 4 象限だけ。札と見込みも変わらない | ほかの全部 |

### 2.2 強調のルール（案）

- 変わった数字・名前の背景を、`tokens.css` にある淡い色にして、2 秒ほどかけて元に戻す。繰り返さない（点滅にしない。G-05 の考えに合わせる）。
- 前の値を、新しい値の横か下に、小さく薄い字で残す（例:「前 187人」）。次の変更まで残す。対象は、人数・金額・札・名前に絞る。
- 色だけに頼らず、「▲ 増えた」「▼ 減った」のような記号か語を添える。
- `prefers-reduced-motion` のときは、薄れる動きをやめて、色と前の値だけにする。
- 読み上げ用の知らせ（`store.ts` の `live`）に、変わった項目を足す。
- 変わらなかった数字は、強調しない。最初の表示と「最初に戻す」のあとも、強調しない。
- 作り方の案: `store.ts` が前の値を持ち、変わった項目の名前（例: `expected`・`need`・`level`）を部品へ渡す。部品は `data-changed="true"` を付ける。数字は core から取る。

## 3. ⑥ 確度の 4 象限

### 3.1 軸

いまの図（`Judge.tsx` の `Scatter`。座標は `scatter.ts` の `QUAD_BOX`）から読み取りました。

| 軸 | 目盛り | 境目（いまは中央線に固定） | 意味 |
| --- | --- | --- | --- |
| 横 | 0・15 万円・60 万円〜 | 15 万円 | 預金額。預金の裏づけ |
| 縦 | 1・3・5 | 3 | 熱量。推しへの熱 |

目盛りは、中央の線を境に、左右（上下）で割合が違います。目盛りの間の読み替えは、担当者が決めます。「推しの登録」は地図の丸の面積（`reg`）、「預金の裏づけ」は横軸と、地図の「払える熱量＝熱量 × 預金額」で出ています。これ以上の出どころ（登録 → 預金が足りる人 → 預金の合計）は、core に無く、確認 6 です。

### 3.2 象限の名前と意味（案）

人数は、core の `demandOf(推し, 市).people` の値です（初めの境目のとき）。

| 位置 | いまの文言 | 名前（案） | 意味 |
| --- | --- | --- | --- |
| 右上 | 熱量が高く、資金もある | いま呼べる | 払える熱いファン。見込み。札の元 |
| 左上 | 熱量は高いが資金が少ない | 熱いが資金が足りない | 預金が増えれば、右上に入る |
| 右下 | 熱量は低いが資金がある | 資金はあるが熱が低い | 熱量が上がれば、右上に入る |
| 左下 | 熱量が低く資金も少ない | どちらも低い | 様子見 |

名前は、使わない語（`tests/unit/forbidden-words.test.ts` の一覧）を避けて、担当者が決めてかまいません。

### 3.3 境目を動かす操作（案）

- 預金額の境目: スライダーと数字の入力。範囲 0〜60 万円。刻み 5 万円。初めは 15 万円。
- 熱量の境目: スライダーと数字の入力。範囲 1〜5。刻み 0.5。初めは 3。
- 「初めの位置に戻す」ボタンを 1 つ置く。
- キーボードで操作できる。押せる部品の高さは 44 px 以上（`--tap`）。
- 置き場所は、⑥の中の、図のすぐ近く。条件を変える場所を 1 か所にまとめるなら、条件の帯でもよい（R-15）。

### 3.4 数え方の制約と、動かしたときの変わり方

core が持つのは、象限ごとの人数（`people`）だけです。人ごとの預金額・熱量はありません。点の位置は、`scatter.ts` が、固定の種の乱数で、象限の中に置いたものです。点の位置は、実際の個人の値ではありません。

| やり方 | 中身 | 良い点 | 気になる点 | 誰が |
| --- | --- | --- | --- | --- |
| A: 見た目の数え直し（11/20 の暫定の案） | 境目の線の位置から、点を数え直す。`quadDots` の `hot` とは別の関数で行う | core を触らない。小さく作れる（工数は未確認） | 数字に根拠が無い。需要の数字を画面の側で作るので、`src/office/README.md` の決まりの例外になる。画面に「点の置き方からの目安（デモ）」と出す | 担当者 |
| B: core に足す | backend に、境目つきの人数計算を足してもらい、`core:sync` で取り込む | 数字が core の値になる | backend の変更・同期・テストが要る。11/20 に間に合うか未確認 | 管理者 |

A は、統括の了承が要ります（確認 1）。了承が出るまで、境目の数え直しは作りません。象限の名前・人数・大きさ・変化の強調は、先に作れます。

A で動かしたときの変わり方（案）:

- 境目の線が動く。点は動かさない。
- 右上（熱量も預金額も境目以上）に入った点だけを濃い色（いまは `--heat-4`）にして、ほかを淡い色（いまは `--gray-300`）にする。
- 象限ごとの人数は、入った点の数 × 1 点あたりの人数（`perDot`）で出す。「約」を付ける。4 つの合計は、境目を動かしても変わらない。
- 境目が初めの位置のときは、core の人数をそのまま出す。
- 札と見込みは、動かさない。札は、core の見込み ÷ 必要人数で決まる（最低人数でも、境目でも変わらない）。画面では、「札の元の見込み」と「境目を動かしたときの右上の人数（目安）」を別の場所に出して、混ぜない。
- 読み上げ用の知らせに、「預金額の境目を 25 万円にしました。熱くて資金もあるファンは、約 N 人です」のように出す。

既存の `tests/unit/scatter.test.ts`（点の座標の範囲と、右上の点の数）は書き換えません（G-24）。`quadDots` の出力は、いまのままにします。

## 4. ③④のデータ

### 4.1 置き場

`src/office/data/` です（統括の決定 2）。置き場そのものは、別の担当が用意します。まだ無いときは、作らずに管理者に聞きます。型と検査（出典と確認日が空でないこと）が入っていれば、それに合わせます。表示用のデータだけを置き、損益・判定・需要の計算には使いません（4.4 節）。

### 4.2 型の案

```ts
/** 実在の会場。出典つきの公開の情報だけ */
interface VenueRecord {
  id: string; // 例: 'FUK-001'（simulator.html の venue_id と同じ形）
  name: string;
  pref: PrefName; // core の型
  city: string; // 住所の市区（例: 福岡市中央区）
  capacity: number; // 収容人数
  capacityBasis: string; // 何の値か（公式・チケットサイトなど二次情報）
  type: VenueType; // ライブハウス・ホール など
  sourceUrl: string; // 収容人数の出典。必須
  checkedOn: string; // 自分が出典を開いて確かめた日 YYYY-MM-DD。必須
  coreVenueId?: VenueId; // core の会場 12 件のどれかに当たるとき
}

/** 過去の公演 */
interface PastEvent {
  venueId: string; // VenueRecord の id
  artist: string; // 芸名・団体名。公開の告知にある名前だけ
  date: string; // YYYY-MM-DD
  sourceUrl: string; // 必須
  checkedOn: string; // 必須
  title?: string;
  genre?: Genre;
}
```

出典と確認日が空のデータは置きません。個人の情報（本名・連絡先・SNS のアカウント）も入れません（運用ルール 5 節）。

### 4.3 実在と架空の見分け方

| 区分 | 何が当たるか | 画面での見せ方（案） |
| --- | --- | --- |
| 実在（出典つき） | 会場の名前・住所の市・収容人数・種類。過去の公演のアーティスト・日付 | ③④の見出しの横に、札「実在の公開情報（出典あり・確認日 YYYY-MM-DD）」。各行に出典のリンク |
| 架空 | 5 組のアーティスト・登録者数・熱量・4 象限の人数・見込み・預金・費用・価格・候補日・上乗せ・札・募集期限 | ①②⑤⑥の見出しの横に、札「デモ用の架空データ」 |

- 札の色は、`tokens.css` の既存の色から選ぶ。区別は、色と文の両方で付ける。
- 実在の会場に、架空の費用と見込みを重ねる所（⑤）には、「会場の名前は実在・数字は架空」と添える。いまの `sideNote`（`text/labels.ts`）の注記を使える。
- 全画面の札 2 枚（`DemoBadge`）は、これまでどおり残す（G-09）。

### 4.4 core の会場との関係

core の会場は 12 件です（`src/core/data/venues.ts`）。`conditionOf(会場の ID)` は、この 12 件の ID だけを受け、知らない ID は例外にします。そのため、`src/office/data/` に足した会場には、到達ライン・必要人数・札を出せません。出せるのは、名前・キャパ・種類・出典・過去の公演です。損益は、シミュレーターのリンクで見せます。core に会場を足すには、backend の変更が要ります（管理者へ。G-17）。

### 4.5 データの出どころ（案）

- `public/simulator.html` の `DATA` に、会場 104 件・公演 496 件があります（出典の URL つき。2026-11-12 時点。班の方が作ったもの）。主なキーは、`venue_id`・`prefecture`・`city`・`venue_name`・`venue_type`・`capacity`・`capacity_basis`・`source_url`・`events`（`date`・`artist`・`event_title`・`genre`・`source_url`）です。
- 案: 読み取って、必要な行を `src/office/data/` に写す。出典の URL を開いて確かめ直し、確認日は確かめた日にする（確認 4）。足りない会場・公演は、公開の告知から調べて足す。
- 257 行目と 258 行目は、とても長い行です。開かずに読みます（運用ルール 7 節）。

### 4.6 字（G-11）

`src/` の `.ts`・`.tsx`・`.css` に書いた字は、フォントの検査（`tests/unit/fonts.test.ts`）が集めます。新しい漢字を足すと検査が落ちて、`npm run verify` が通りません。核のフォントの合計は、上限 400,000 B に対して 353,176 B です（`public/fonts/` の 3 本の大きさの合計）。足せる漢字は 60 字ほどと試算しています（試算。実測ではない）。落ちたら、`docs/フォント.md` の 5 節に沿い、Python と元のフォントが無いときは、漏れた字の一覧を添えて管理者に頼みます（確認 5）。

PC と iPad が基準です。iPad は機種で横幅が違い、どの機種・どの向きかは、確認 2 で決めます。目標は、幅 1280 × 高さ 800 で、①〜⑥の見出しに、スクロール 800 px 以内で届くことです（確認 2 の案）。
