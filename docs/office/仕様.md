# 仕様（事務所向けの画面。大まかな案）

`要件.md` の R-xx を、どんな画面にするかの案です。細部は、担当者が決めます。

- 状態: 案（2026-11-14）。「案」と書いた所は、担当者が変えてかまいません。変えてはいけないのは、7 節の決まりです。
- 統括が決めたこと（`要件.md` の 8 節）を前提にしています。境目の数え方は案 A（3.4 節）、スクロールの基準は「1280 × 800 で、①〜⑥の見出しが全部見える」（6 節）です。
- 計算（損益・判定・需要）は、`src/core/` の値を使います。画面の側で式を書きません（`src/office/README.md`）。

## 1. 画面の配置

### 1.1 いまの配置

縦 1 列です。「上の帯 → 推し 5 組 →（地図 | 会場の候補）→ 判定（開催条件・満たせるか | 4 象限）」の順です。地図が高く、判定は 937 px から始まるので、画面の高さ 800 px では見えません（`要件.md` 3 節の測った事実）。

### 1.2 案を 2 つ

どちらも、幅 1280 px 以上が基準です。上の帯と、その下の「条件の帯」（推し 5 組・② 集まる人数・選んでいる市と会場）は共通です。

**案 A: 左から右へ流れる 3 列**

```
┌──────────────┬──────────────┬──────────────┐
│ ①② 地図・順位   │ ③④ 会場の候補   │ ⑤⑥ 損益の要約   │
│    集まる人数    │    過去の公演    │    確度・4 象限  │
└──────────────┴──────────────┴──────────────┘
```

**案 B: 左で選び、右で結果を見る 2 列**

```
┌─────────────────────┬─────────────────────┐
│ 左（選ぶ）            │ 右（結果を見る）        │
│ ① 需要の地図と市の順位  │ ⑥ 確度（札・横棒・4 象限・境目）│
│ ③ 会場の候補           │ ⑤ 損益の要約            │
│                      │ ④ 過去の公演            │
└─────────────────────┴─────────────────────┘
```

案 B は、右の列の並びが、番号の順（①→⑥）と違います。商談の流れを「左で選ぶ → 右で結論を見る」と考えて、統括が強くしたい⑥を右の最上段に置きました。区画の見出しには ①〜⑥ の番号を付けて、話す順を示します。

### 1.3 比べる

| 見る点 | 案 A（3 列） | 案 B（2 列） |
| --- | --- | --- |
| 商談の流れ | 左から右へ、①〜⑥の順に一直線 | 左で選び、右で見る。番号の順とは違う |
| ⑥の大きさ | 列の幅が約 370 px。4 象限は、いまの 574 px から小さくなる | 右の列が約 570 px。いまの 4 象限のカードと同じ大きさ |
| 変わった所を見る場所 | 中央と右に分かれる | 右の列に集まる |
| ①〜⑥の見出しが、1280 × 800 でスクロールなしに見える見込み | 各列が短く、収まりやすい | 左の列が長い（地図 670 px）。地図を小さくする必要がある。右の列は、⑥を小さくする必要がある（下の「気になる点」）。未確認 |
| いまの部品の使い回し | 3 列の CSS を新しく作る | `.top`（2 列）と `.judge`（2 列）に近く、並べ替えで足りる |

**推す案は B です。**

1. 条件を変えて「どこが変わったか」を見る目の動きが、左（操作）から右（結果）へ 1 本に決まる（Q-12）。
2. ⑥に、幅の半分を使える（統括の優先。決定 3）。

気になる点は、縦の長さです（目標は、幅 1280 × 高さ 800 で、①〜⑥の見出しが全部見えること）。

- 左の列: 地図の高さを 400〜450 px に抑える案です。
- 右の列: いまの 4 象限のカードは、高さ 593 px です（`要件.md` の測った事実）。このままだと、⑤と④の見出しが、800 px より下に出ます。⑥は約 300 px に収める必要があります（図を小さくして、象限の名前と人数を横に並べるなど）。
- 見出しが見えればよく、区画の中身（会場の一覧・公演の一覧）は、区画の中でスクロールしてよい案です。
- 作って測って、B で収まらないときは、A に切り替えてかまいません（担当者が決める）。

## 2. 条件を変えたときの見せ方（R-14）

### 2.1 どの操作で、どこが変わるか

いまのコード（`store.ts`・`view.ts`・core）から読み取りました。

| 操作 | 変わる区画 | 変わらない区画 |
| --- | --- | --- |
| 推しを切り替える | ①（丸・順位）。⑥（見込み・札・横棒・4 象限） | ③④。⑤の到達ライン・必要人数・上乗せ（会場の区分で決まるため） |
| 市を選ぶ | ③の候補。⑥の見込みと 4 象限。選んでいた会場・費用・最低人数は消える | ① |
| 集まる人数（②）を変える | ③の並びと規模感 | ⑤⑥（人数は会場の絞り込みにだけ使う。確認 8） |
| 会場を選ぶ | ④⑤。⑥の札と横棒（必要人数が変わる。見込みは変わらない） | ① |
| 費用・最低人数を書き換える | ⑤の到達ライン・必要人数・成立の条件。⑥の札と横棒。最低人数だけなら、成立の条件と注意の文だけ（札は必要人数で決まる） | ①③④ |
| 境目を動かす | ⑥の 4 象限だけ。札と見込みも変わらない | ほかの全部 |

### 2.2 強調のルール（案）

- 変わった数字・名前の背景を、`tokens.css` にある淡い色にして、2 秒ほどかけて元に戻す。繰り返さない（点滅にしない。G-05 の考えに合わせる）。
- 前の値を、新しい値の横か下に、小さく薄い字で残す（例:「前 187人」）。次の変更まで残す。対象は、人数・金額・札・名前に絞る。
- 色だけに頼らず、「▲ 増えた」「▼ 減った」のような記号か語を添える。
- `prefers-reduced-motion` のときは、薄れる動きをやめて、色と前の値だけにする。
- 読み上げ用の知らせ（`store.ts` の `live`）に、変わった項目を足す。
- 変わらなかった数字は、強調しない。最初の表示と「最初に戻す」のあとも、強調しない。
- 作り方の案: `store.ts` が前の値を持ち、変わった項目の名前（例: `expected`・`need`・`level`）を部品へ渡す。部品は `data-changed="true"` を付ける。数字は core から取る。

人数は、core の `demandOf(推し, 市).people` の値です（初めの境目のとき）。

### 3.3 境目を動かす操作（案）

- 預金額の境目: スライダーと数字の入力。範囲 0〜60 万円。刻み 5 万円。初めは 15 万円。
- 熱量の境目: スライダーと数字の入力。範囲 1〜5。刻み 0.5。初めは 3。
- 「初めの位置に戻す」ボタンを 1 つ置く。
- キーボードで操作できる。押せる部品の高さは 44 px 以上（`--tap`）。
- 置き場所は、⑥の中の、図のすぐ近く。条件を変える場所を 1 か所にまとめるなら、条件の帯でもよい（R-15）。

### 3.4 数え方の制約と、動かしたときの変わり方

core が持つのは、象限ごとの人数（`people`）だけです。人ごとの預金額・熱量はありません。点の位置は、`scatter.ts` が、固定の種の乱数で、象限の中に置いたものです。点の位置は、実際の個人の値ではありません。

統括が決めました（確認 1）。**11/20 までは、案 A で、「目安」として出します。** 正しい計算（案 B）は、発表のあとに backend に足します。今回は作りません。

| やり方 | 中身 | 良い点 | 気になる点 | 誰が |
| --- | --- | --- | --- | --- |
| A: 見た目の数え直し（11/20 まで。決定） | 境目の線の位置から、点を数え直す。`scatter.ts` に、`quadDots` の `hot` とは別の関数として足す | core を触らない。小さく作れる（工数は未確認） | 数字に根拠が無い。画面に「目安（デモ）」と明記する。需要の数字を画面の側で作るので、`src/office/README.md` の決まり（数字は core から取る）の、統括が認めた例外 | 担当者 |
| B: core に足す（発表のあと。今回は作らない） | backend に、境目つきの人数計算を足してもらい、`core:sync` で取り込む | 数字が core の値になる | backend の変更・同期・テストが要る | 管理者 |

A で動かしたときの変わり方:

- 境目の線が動く。点は動かさない。
- 右上（熱量も預金額も境目以上）に入った点だけを濃い色（いまは `--heat-4`）にして、ほかを淡い色（いまは `--gray-300`）にする。
- 象限ごとの人数は、入った点の数 × 1 点あたりの人数（`perDot`）で出す。「約」を付ける。4 つの合計は、境目を動かしても変わらない。
- 境目が初めの位置のときは、core の人数をそのまま出す。動かしたときは、人数に「目安（デモ）」と添える。
- 札と見込みは、動かさない。札は、core の見込み ÷ 必要人数で決まる（最低人数でも、境目でも変わらない）。画面では、「札の元の見込み」と「境目を動かしたときの右上の人数（目安）」を別の場所に出して、混ぜない。
- 読み上げ用の知らせに、「預金額の境目を 25 万円にしました。熱くて資金もあるファンは、約 N 人です」のように出す。

既存の `tests/unit/scatter.test.ts`（点の座標の範囲と、右上の点の数）は書き換えません（G-24）。`quadDots` の出力は、いまのままにします。

### 4.4 core の会場との関係

core の会場は 12 件です（`src/core/data/venues.ts`）。`conditionOf(会場の ID)` は、この 12 件の ID だけを受け、知らない ID は例外にします。そのため、`src/office/data/` に足した会場には、到達ライン・必要人数・札を出せません。出せるのは、名前・キャパ・種類・出典・過去の公演です。損益は、シミュレーターのリンクで見せます。core に会場を足すには、backend の変更が要ります（管理者へ。G-17）。

**表示と計算は、別の部品に分けます**（検査が見ます）。

- データを読む部品（会場のカード・過去の公演の一覧）は、表示だけを行います。core の計算の関数（`conditionOf`・`demandOf`・`levelOf` など）を呼びません。
- いまの `SidePanel.tsx` は、`conditionOf`・`demandOf` を呼んでいます。この部品はデータを読ませず、データを読む部品を別に作って、計算の結果は props で渡します。
- `view.ts`・`scatter.ts`・`store.ts` は、データを読みません。データだけの会場を選ぶときは、`store.ts` は文字の ID だけを持ち、データの読み取りは部品で行います。
- `src/core/`・`src/fan/`・`src/shared/`・`src/presenter/` は、データを読みません。
- 並べ替えと、規模感（キャパ ÷ 人数）は、表示の範囲です。データを読む部品の中で行ってかまいません。損益や判定に見える表示にはしません。

### 4.5 データの出どころ（確認 4）

- 統括が決めました。`public/simulator.html` の中の会場と公演のデータを、読み取って `src/office/data/` に写してよいです。出典の URL と確認した日付を付けます。**シミュレーターの中に出典があるものだけ**です。写真は、11/20 までは使いません。

### 9.3 収支シミュレーターの計算（M-14〜M-18）

```
経費       ＝ 会場費 ＋ 制作費 ＋ 移動・宿泊
最低条件   ＝ 切り上げ（（経費 ＋ 出演料 ＋ 利益（希望額））÷（1 − 0.10））
必要人数   ＝ 切り上げ（最低条件 ÷ チケット価格）
集まる合計 ＝ キャパ × チケット価格 ＋ 3 つのプランの上乗せ（満席のとき。暫定）
手数料     ＝ 切り上げ（集まる合計 × 0.10）
全体利益   ＝ 集まる合計 − 手数料 − 会場費 − 制作費 − 出演料 − 移動・宿泊費
```

- 最低条件と手数料を、どちらも 1 円未満で切り上げると、最低条件ちょうど集まったとき、全体利益が利益（希望額）と 1 円の違いもなく一致します。
- 利益（希望額）の初めの値は、区分ごとに「これまでの利益 − これまでの最低条件 × 0.10」で逆算しました。最低条件は、どの区分もこれまでと同じ値です。
