## 4. うまくいった状態

## 5. 見本の Artifact の形

形だけを書きます。会場・公演・数字の中身は、この文書に写していません。

- 九州 7 県の地図に、実在の会場を円で出す。円の大きさは、収容人数。
- 同じ地図に、推しの需要を、市ごとの円で重ねる。
- 条件は、推し・集まる人数・県・種類。過去の公演のジャンルでも絞れる。
- 凡例は、「推しの需要（預金の裏づけあり）」「人数に合う会場」「そのほかの会場」「円の大きさ＝収容人数」。
- 進め方の説明が帯に出る。推しを選ぶ → 需要の濃い街を選ぶ → 近くの会場 → 損益を試算、の順。
- 右側に、需要の濃い街の順位、需要の出どころ（登録した人 → うち預金が申込額以上の人 → その預金の合計の 3 段）、近い規模の会場の一覧、損益の試算、会場の詳細（過去の公演）が並ぶ。
- 収容人数と公演は、各行の出典の URL で確かめられるものだけを載せ、データの日付は 2026-11-12。

## 6. 決まっていること（統括。2026-11-14）

要求を、画面の作りに落とすときの前提です。

1. 実在の会場と、実際の公演のデータを使ってよい。ただし、出典つきの公開の情報だけ。需要・預金・損益の数字は、架空のまま。札「デモ用の架空データ」「動作確認用のデモ画面です」は残す。実在のデータと架空の数字が混ざる所は、どれが実在でどれが架空かが、画面で分かるようにする。
2. 事務所向け専用のデータ置き場 `src/office/data/` を作り、表示用のデータ（会場・過去の公演）は、担当者がそこに足してよい。計算（損益・判定・需要）は、これまでどおり `src/core/`（担当者は変えない）。
3. 発表（11/20）までの優先は、⑥（確度・4 象限と、境目を動かす操作）と、1 つの画面にまとめること。③④は、データが用意できた分だけ。
4. 収支シミュレーター（⑤。`public/simulator.html`）は、別のページのまま残す。ダッシュボードには、選んだ会場の損益の要約だけを出す。
