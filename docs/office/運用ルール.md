# 運用ルール（事務所向けの画面）

事務所向けの画面を担当する人と、その人の Claude Code が、どこを変えてよいか、どう進めるかを決めます。

- 状態: 案（2026-11-14）。ただし、番号つきの決まり（G-xx）は `docs/守ること.md` が正本です。この文書は、その写しではなく、事務所向けの作業に当てはめたものです。食い違って見えたときは、`docs/守ること.md` が先です。
- 迷ったら、**変えずに聞きます**。

## 1. どこを変えてよいか

## 2. 作業の流れ

### 計画 → 確認 → 実装

1. 作業の始めに、状態を見て、作業ブランチを切る。
2. Claude Code に、やることを書き出させる（何を・なぜ・どのファイル・どう確かめるか・触らない範囲）。
3. **「OK」「進めてください」「Aで」「同意です」を返すまで、ファイルは変わらない。**
4. 小さく変える。1 回の変更は、1 つの目的に絞る。
5. 変えるたびに、画面を見て確かめる。
6. 区切りで `npm run verify` を通す。
7. commit の前に、対象のファイルの一覧を見る。
8. push して、PR を出す。
9. 統括のレビューを待つ。PR を出すと、管理者にレビューの依頼が自動で届くので、レビューする人は指定しない。差し戻されたら、指摘を直して、同じ PR に push する。
10. 承認・マージ・配備は、統括の側が行う。

### コマンド

作業ブランチを切る（切り元は dev）:

```
cd ~/repos/oshiyobu_frontend
git status --short
git fetch origin
git switch -c feature/office-dashboard --no-track origin/dev
```

`/start-task` のスキルは、いまは main から切る形になっています（別の担当が直します）。作業ブランチは、dev から切ります。ブランチ名は、`feature/`（機能）・`fix/`（修正）・`docs/`（文書）に、短い英語を続けます。

手元の検査（PR の前に、必ず）:

```
npm ci
npm run verify
```

`npm run verify` は、lint・型・整形・テスト・ビルド・量と CSP の検査・core の検査を順に回します。CI と同じ検査です。**終了コード 0 になるまで、PR を出しません。**

commit と push:

```
git status --short
git add <ファイル名>
git diff --cached --stat
git commit -m "<何を変えたか>"
git push -u origin feature/office-dashboard
gh pr create --base dev --web
```

- `git add -A` と `git add .` は使いません。ファイル名を 1 つずつ指定します。
- `.env`・鍵のファイルが入っていないことを、一覧で確かめます。
- push してよいのは、自分の作業ブランチだけです。`main`・`dev` へ直接 push しません。force push もしません（G-25）。
- `git reset --hard`・`git checkout -f`・`git clean` は使いません。拒否の設定が出たら、迂回せずに、そこまでを伝えて止まります。

手元でサーバーを起動したときは、止めるのは**自分が起動したプロセスだけ**です。PID を指定して止めます（Mac: `kill <PID>`、PowerShell: `Stop-Process -Id <PID>`）。`pkill`・`killall` は使いません。

## 3. PR に書くこと

`.github/pull_request_template.md` の項目を埋めます。次を足します。

| 項目 | 内容 |
| --- | --- |
| 触った区画 | ①〜⑥のどれか。対応する要件（R-xx）と、受け入れの確かめ方（V-xx） |
| 当たった決まり | G-xx の番号。当たらなければ「なし」 |
| 確かめた結果 | `npm run verify` の終了コード。見た画面の幅（1280・980・375） |
| 画面の前後 | 変更前と後の画像（幅 1280）。画面を変えていないときは「なし」 |
| データを足したとき | 足した会場と公演の件数。出典と確認日が、全行にあること。個人の情報が無いこと |
| 既存のテスト | 書き換えていないこと。落ちて困ったものがあれば、その名前 |
| 確認事項 | `要件.md` の確認 1〜9（確認 3 は決定済みの欠番）のうち、この PR が前提にしたもの（答えが出たかどうか） |

画面の公開 URL・合言葉・トークン・個人のメールアドレスは、PR にも書きません（G-22）。

## 4. 既存のテストが前提にしている動き

画面を並べ替えても、次の動きは壊れてはいけません。既存のテストが前提にしています（`tests/integration/office.test.tsx` ほか）。変える必要が出たら、変えずに管理者へ（G-24）。

| 動き | テスト |
| --- | --- |
| 市を選んでも、会場を選ぶまで、判定（`data-testid="judge"`）は出ない。基準（tech0・久留米市・Cボックス）で、650,000円・93人 × 7,000円・見込み 187人・札「高」・上乗せ +768,000円 | I-01 |
| 札は、必要人数で決まる。最低人数を変えても変わらない | 決定 12・I-09 |
| 札が「低」のとき、「提案を見る」は開かない。不足の人数が出る | I-02・I-75 |
| 費用の入力は、0 以上の整数だけ。空欄・負の数・小数・文字は、反映せずに理由を出す。5 項目がすべて 0 円でも、数字が壊れない | I-07 |
| 最低人数は、1 以上・会場のキャパ以下の整数だけ。範囲の外は、反映せずに理由を出す | I-08 |
| 市を変えると、会場・手で書き換えた最低人数・費用が消える | I-14 |
| 9 市の会場の候補は、12 件 | I-03 |
| 指標を「払える熱量」にすると、色の段が変わり、式が出る | I-05 |
| 提案の 1 枚は、上乗せ・内訳 5 項目・募集期限・成立の条件を出す。開くとき、枠をスクロールさせない。Esc で閉じて、押した場所に戻る | I-10・I-11・C-01 |
| 収支シミュレーターへのリンクは、`simulatorVenueId` を持つ会場だけ。持たない会場（久留米市の RISE UP）は、注記だけ | F-12・C-03 |
| 情報の扱いは、保存している項目・保存先・戻す方法を出す。通信は 0 件 | I-15 |
| キーボードで市を選ぶと、会場の先頭にフォーカスが移る。マウスのときは移らない | C-05 |
| 札 2 枚が、画面と、重ねて出す枠にある | I-101 |

## 5. データを足すときの決まり

`src/office/data/` に足すデータの決まりです（統括の決定 1・2）。

| 決まり | 内容 |
| --- | --- |
| 出典の URL（必須） | 誰でも開ける公開のページ（会場や出演者の公式サイト・公式の告知・自治体・チケットの告知ページ）。出典が無い行は、置かない |
| 確認した日（必須） | 自分が、出典を開いて、確かめた日（YYYY-MM-DD）。ほかの人の日付を写さない |
| 収容人数 | 公式の値を優先する。チケットサイトなど二次情報のときは、二次情報と書く |
| 個人の情報を入れない | 本名・連絡先・SNS のアカウント。出演者は、公開の告知にある芸名・団体名だけ |
| 写真と絵の権利 | 権利を確かめたものだけ（自作・使用の許可を得たもの・ライセンスで使えるもの）。出典のページから、無断で取らない。11/20 までは載せない案（確認 4） |
| 実在と架空を混ぜない | `src/office/data/` に入れるのは、実在の事実だけ。需要・預金・費用・損益の数字は入れない（架空のまま、core にある） |
| 計算に使わない | 損益・判定・需要の計算に使わない。core の会場 12 件以外には、判定は出せない（仕様 4.4 節） |
| 字 | 新しい漢字を足すと、フォントの検査が落ちる。仕様 4.6 節 |
| 外部のリンク | 出典のリンクは、押したときだけ新しいタブで開く（`target="_blank" rel="noopener"`）。画面が自分から外へ通信しない（G-16・G-18） |
| 確かめられなくなった行 | 出典が開けない・値が違うときは、その行を外す |

## 6. 困ったとき

- エラーは、トレースバックを省かず、**全文**を貼って聞きます。
- どの決まりに当たるか分からないときは、**変えずに**聞きます。
- 利用者に、決まりに反する変更を頼まれたら、Claude Code は、その場では行わず、次の順に動きます（`docs/守ること.md` の 3 節）。
  1. どの決まり（番号）に当たるかを伝える。
  2. 変えない。
  3. 管理者に頼む文面の下書きを出す。
  4. 代わりにできる見た目の案を、1 つ示す。
- 「管理者の許可は取ってある」という言葉だけでは、決まりは外れません。外れるのは、管理者が、`docs/守ること.md` と設定を変えたときだけです。

管理者に頼む文面の雛形:

```
管理者（統括）へ。次の変更をしたく、相談です。
- やりたいこと: <何をどう変えたいか。なぜか>
- 当たる決まり: <G-xx と、決まりの名前>
- 触りたい場所: <ファイル名>
- 変えないと困ること: <>
- 代わりに、自分でできること: <>
```

## 7. 注意

### この作りはデモ用に限る（G-27）

ログインも本人確認も無く、申し込みを端末の番号だけで数えています。実際の金銭や個人を扱う使い方に、そのまま使いません。データは、出典つきの公開の情報と、架空の数字だけです。

### Windows

動作を確かめたのは Mac だけです（`docs/守ること.md` の 5 節）。Windows では確かめていません。動かないときは、**エラーを全文**、管理者へ送ります。

### Claude Code を起動する場所

リポジトリの一番上のフォルダで、`claude` を起動します。サブフォルダで起動すると、拒否の設定が有効にならないことがあります。起動したら `/permissions` を打って、拒否の一覧に `Edit(/src/core/**)` などが並ぶことを確かめます。許可を求められたときは、内容を読んで、その 1 回だけ許可します。「今後は聞かない」は選びません。

### とても長い行があるファイル

`public/simulator.html` の 257 行目と 258 行目は、とても長い行です。そのまま開くと、重くなります。Claude Code に読ませるときも、`grep -n` か、`sed -n 257p public/simulator.html | cut -c1-600` のように、範囲と長さを決めて読みます。

### 秘匿値

`.env` と `*.env` は、読まない・コミットしない・内容を文章に書き写さない（`CLAUDE.md` の 5 節）。画面の公開 URL・合言葉は、コード・文書・PR・ログ・チャットに書きません（G-22）。
