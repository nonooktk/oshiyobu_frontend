# デプロイ手順

手元の変更を本番に反映するまでの流れと、失敗したときの戻し方です。

デプロイ先は **Azure Static Web Apps（Free）**です。次の表のとおり決まっています（設計 D-22・D-27・D-29）。

## 決まっていること

| 項目 | 内容 |
| --- | --- |
| デプロイ先 | 画面は Azure Static Web Apps（Free）の `swa-oshiyobu-nonooktk`。API は App Service（既存の B1 に相乗り）の `app-oshiyobu-api-nonooktk`（API は backend のリポジトリ。担当者の範囲外） |
| CI の中身と、必須にするチェック | job `verify` だけが必須。PR と、main・dev への push で動く。中身は `npm ci` → `npm run verify`（lint → 型 → 整形の確認 → テスト → ビルド → `check:budget --strict-images` → `check:csp` → `core:check`）。手元で同じことを行うコマンドは、下の「手元で CI と同じ検査をする」 |
| プレビュー環境 | まだありません（`preview.yml` は未整備）。PR の確認は、手元で `npm run build` のあと `npm run preview`（<http://localhost:4173/>）で行います |
| 本番への反映 | `.github/workflows/deploy.yml`。**GitHub の「Actions」画面から手で起動したときだけ動きます**（`workflow_dispatch`）。main に入っただけでは、本番は更新されません。11/18 の承認のあと、統括が PR で main への push を足します |
| 本番の URL | 11/18 の承認のあとに、統括が追記します。それまで、README・Actions のログ・PR に URL を書きません。QR に入れるのは `/fan/`、発表者用は `/presenter/` |
| PR のマージ方法 | **Squash and merge だけ**。戻し方は `git revert <コミットの ID>` の 1 通り |
| マージと承認ができる人 | 統括だけ。担当者は PR を出すところまで |
| main の直接 push を止める設定 | 設定済み（PR 必須・承認 1 件・CODEOWNERS）。統括が、Required status checks に `verify` を足し、マージ方法を Squash だけにします |
| 前の版に戻す操作 | revert の PR（標準）。緊急のときは、統括が、GitHub の画面で、前に成功した `deploy` の実行を **Re-run** する（担当者と Claude Code はしない） |
| 発表者の PC の退避 | `npm run build` の済んだフォルダを置き、`npm run preview`（localhost）で同じビルドを開きます。API がなくても動きます（回線が切れても発表を続けるため） |

### 手元で CI と同じ検査をする

```
npm ci
npm run verify
```

`verify` は、lint → 型 → 整形の確認 → テスト → ビルド → `check:budget --strict-images` → `check:csp` → `core:check` を順に実行し、最後に、どれが落ちたかと、次に見る場所を日本語でまとめます（CI も、これを呼びます）。API との通信まで確かめるときは `npm run accept`（`docs/検収.md`）。

実ブラウザの速さ・CSP・共有メーターの試験は `npm run e2e`（任意。`docs/はじめに.md` の C 節）。

## 全体の流れ

```
ローカルで確認 → PR を出す → CI が緑 → 手元のプレビューで確認 → 承認 → main に入れる → 統括が deploy を手で起動 → 反映後に確認
```

順番は飛ばしません。どこかの段で止まったら、次へ進まず、止まった段の「次へ進める条件」を確かめます。

## 各段の担当と、次へ進める条件

| 段 | 誰が | やること | 次へ進める条件（出るもの） |
| --- | --- | --- | --- |
| 1. ローカルで確認 | 担当者（Claude Code と一緒に） | アプリをローカルで動かして見る。`/pre-deploy-check` を実行する | 表がすべて ○ になる。変えた画面をスマホと PC の幅で見て、崩れがない |
| 2. PR を出す | 担当者 | 作業ブランチを push して、PR を作る | PR の URL が出る。PR の本文に、ひな形の項目がすべて埋まっている |
| 3. CI が緑 | 自動（GitHub Actions） | PR のチェックが走る | PR のチェックがすべて成功になる |
| 4. 手元のプレビューで確認 | 担当者と承認者 | `npm run build` のあと `npm run preview` で画面を見る | 見た人が「見て OK」と PR にコメントしている |
| 5. 承認 | 承認者（統括） | 内容を見て承認する | 「OK」「進めてください」「Aで」「同意です」のどれかが PR かチャットに残っている |
| 6. main に入れる | 承認者（GitHub の画面で PR をマージ） | PR の画面でマージを押す | PR が「Merged」になる |
| 7. 反映 | 統括（GitHub の「Actions」画面） | `deploy` を**手で起動**する。反映のあと、自動の確認（下の「反映と自動の確認」）が走る | 反映の実行が成功になる |
| 8. 反映後に確認 | 担当者 | 本番で、変えた画面と主要な動き 1 本を見る | 見えるべきものが見えている。「デモ用の架空データ」の表示がある |

担当者と Claude Code は **6（main に入れる）と 7（反映）を行いません。** 手元から `az` や `swa` で反映することもしません。

### 2. PR を出す

作業ブランチを push します（Claude Code が実行前に確認を取ります）。

```
git push -u origin <ブランチ名>
```

PR を作ります。ブラウザで PR の作成画面が開きます。

```
gh pr create --web
```

本文の欄にひな形（`.github/pull_request_template.md`）が入っていれば、項目を埋めます。入っていなければ、ひな形の中身を貼って埋めます。

### 3. CI が緑

PR の画面の「Checks」を見るか、次を実行します。

```
gh pr checks <PR の番号>
```

すべて成功になるまで次へ進みません。失敗したときは、エラーを**全文**貼って聞きます。

### 4. プレビューで確認

手元で `npm run build` のあと `npm run preview` を実行し、<http://localhost:4173/> で、変えた画面を見ます（スマホの幅と PC の幅の両方）。

### 6. main に入れる

承認者が GitHub の PR の画面でマージします。担当者は押しません。Claude Code も行いません（`gh pr merge` は拒否しています）。

### 7. 反映（統括が手で起動する）

**main に入っただけでは、本番は更新されません。** 統括が、GitHub の「Actions」画面で `deploy` を選び、「Run workflow」を押します（`workflow_dispatch` だけ。担当者と Claude Code は押しません。`gh workflow run` は拒否しています）。

`deploy` の中身は、次の順です。

1. `npm ci`
2. `npm run core:check -- --remote`（`src/core/` が、lock のコミットの内容と一致すること）
3. `npm run build`（接続先は、Variables の `VITE_API_BASE`）
4. `npm run check:budget -- --strict-images`・`npm run check:csp`（元絵の形式〈jpg・png〉のまま配っていないことも、エラーにする。手元の `npm run verify` と CI も、同じ指定で回す）
5. Azure Static Web Apps に配備（配備トークンは Secrets の `AZURE_STATIC_WEB_APPS_API_TOKEN`）
6. **反映後の自動の確認**（`scripts/check-deployed.mjs`）: `/`・`/fan/`・`/presenter/`・`/simulator.html` が 200 であること、圧縮（`Content-Encoding`）・CSP・`X-Robots-Tag: noindex`・`Cache-Control`（HTML は `no-cache`、`/bundle/*` は `immutable`）が付くこと、API の `/healthz` の `coreVersion` が `core.lock.json` の版と一致すること。失敗は、`deploy` の失敗として残ります

反映の実行は「Actions」タブで見られます。

```
gh run list --limit 5
```

> [!warning] 配備したら、開き直す
> 配備の前から開いたままの画面は、古い版の「遅れて読むファイル」が見つからなくなることがあります。**発表の直前に、開いたままの端末がある時間帯の配備は避け、配備したら、端末の画面を開き直します。**

**検証用の公開と QR の順**（設計 D-22）:

1. 11/15 の夜: Static Web Apps を作り、URL を API の `CORS_ORIGINS` に入れる。
2. 11/16 の午前: **検証公開**。`deploy` を手で起動する（承認は、G1 のときに統括が、API の配備・負荷の試験とあわせてする）。圧縮・HTTP/2・ヘッダー・CSP・API との接続を確かめ、速さを測る。機能は途中でよい。
3. **URL を班の外へ出すこと（README・公開のチャンネル・投稿文）と、QR を作ることは、11/18 の承認のあと。** それまでは、全ページに `noindex` が付いています。

### 8. 反映後に確認

1. 本番の URL を開く（URL は統括から聞く。このリポジトリには書きません）。
2. 変えた画面が想定どおりに出ているか見る。
3. 全画面に「デモ用の架空データ」の表示が出ているか見る。
4. 主要な動きを 1 本、最初から最後まで通す。どの動きを通すかは承認者が決める。
5. 結果（OK か、見えたもの）を PR にコメントする。

書き込みを伴う動きを通すときは、**テスト用のデータだけ**を使います。本物の利用者のデータは書き換えません。

## 失敗したときの戻し方

本番が壊れたら、**main を 1 つ前の状態に戻す PR を出して、同じ流れで反映します。** 強制 push はしません。

次の操作は**どんなときも行いません**。

- 強制 push（`git push --force` など）
- `git reset --hard` で main を巻き戻す
- 手元から `az` や `swa` で本番を入れ替える

### 手順

1. **止まって承認者に伝える。** いつ、どの PR を反映したか。何が壊れているか。画面の写真かエラーの**全文**。
2. **戻す PR を作る。** どちらか 1 つの方法で行う。
   - **方法 A（簡単）**: GitHub で戻したい PR（マージ済み）の画面を開き、下のほうにある「Revert」を押す。戻すための PR が自動で作られる。書き込み権限が必要。
   - **方法 B（コマンド）**: 次の順に実行する。

     ```
     git switch main
     git pull --ff-only
     git switch -c fix/revert-<PR の番号>
     git log --oneline -n 10
     ```

     戻すコミットの ID を `git log` の出力から探します。このリポジトリのマージ方法は **Squash and merge だけ**なので、戻し方は 1 通りです。

     - `git revert <コミットの ID>`

     そのあと、作業ブランチを push して PR を作る（「2. PR を出す」と同じ）。
3. **戻す PR も同じ流れで進める。** CI、承認、承認者によるマージ、自動の反映、反映後の確認。本番が壊れているときは、承認者に「戻す PR を出す」と先に伝えて、優先して見てもらう。
4. **戻ったことを確かめる。** 「8. 反映後に確認」と同じ。
5. **原因を調べて直す。** 元の変更を入れ直すときは、新しいブランチで直して、新しい PR にする。

### 緊急のとき（統括だけが行う）

revert の PR を待てないときは、統括が、GitHub の「Actions」画面で、**前に成功した `deploy` の実行を開き、「Re-run all jobs」を押します**。担当者と Claude Code は行いません。戻したあとは、「8. 反映後に確認」を行い、そのあとで revert の PR を出します。戻したあとも、端末の画面は開き直します。

## 秘匿値の扱い

- デプロイに必要な値（トークンなど）は、統括（または配備の担当）が GitHub の Actions の Secrets・Variables に登録します（名前は下の表。値はどこにも書きません）。担当者と Claude Code は、値を見ません・書きません・持ちません。キー名を足したいときは統括に依頼します。
- **秘匿値を commit・push・PR に載せてしまったとき**は、すぐに止まって統括に伝えます。載せた値は使えなくする必要があります（あとから消しても履歴に残るため）。強制 push で履歴を書き換えて消そうとしないでください。

### Secrets と Variables の名前（値は書かない）

| 種類 | 名前 | 中身 | 使う所 |
| --- | --- | --- | --- |
| Secret | `AZURE_STATIC_WEB_APPS_API_TOKEN` | Static Web Apps の配備トークン | `deploy.yml` の配備 |
| Secret | `SWA_BASE_URL` | 配備先の URL（ログに出さないため Secret にする） | `deploy.yml` の反映後の確認 |
| Variable | `VITE_API_BASE` | API の接続先（origin。例: `https://…`）。画面の接続と CSP の `connect-src` に入る。未設定なら、サーバーなしで動く | `deploy.yml` のビルド |
| Variable（任意） | `VITE_SHARED_METER` | `on` にすると、ファン向けが共有メーター（全員の人数を API で集める形）で動く。未設定（既定）は、ひとり体験で、`VITE_API_BASE` があっても、ファン向けは API を呼ばない。いまの `deploy.yml` はこの変数を渡していない。共有に戻すときは、ビルドの 3 か所（`env:`）に `VITE_SHARED_METER: ${{ vars.VITE_SHARED_METER }}` を足して、Variables に `on` を登録する | `deploy.yml` のビルド |

## 付録: Claude Code に許していない操作（`.claude/settings.json`）

次の操作は設定ファイルで拒否しています。拒否の設定は許可の設定より優先されます。Claude Code で `/permissions` を実行すると、一覧を見られます。

| 種類 | 拒否している操作 | 理由 |
| --- | --- | --- |
| main への push・強制 push | `git push` のうち、引数のないもの・`origin` だけのもの・`HEAD` を指すもの・main 宛のもの・強制（`--force`、`-f`、`+`）・リモートの削除（`--delete`）・`--mirror`・`--tags` | main に直接入れない。push してよいのは `git push -u origin <作業ブランチ名>` だけ |
| 変更を消す操作 | `git reset --hard`、`git checkout -f`、`git switch -f`、`--force`、`--discard-changes`、`git clean` | 作業中の変更が戻せなくなる |
| git の別の書き方 | `git -C …`、`git -c …` | 上の拒否をすり抜けるのを防ぐ |
| マージ・デプロイ | `gh pr merge`、`gh api`、`gh workflow run`、`gh release`、`az`、`azd`、`swa`、`npx swa`、`vercel`、`netlify` | マージとデプロイは承認を得た人が決まった流れで行う |
| 秘匿値の読み取り | `.env`、`.env.*`、`*.env`（`.env.example` は読める）、`~/.ssh`、`~/.azure`、`~/.config/gh` | 秘匿値を読まない |

Windows の PowerShell で動く Claude Code にも、同じ規則を `PowerShell(...)` の形で置いています。

### この拒否でできないこと（公式ドキュメントの記載）

- コマンドの拒否は、書かれた文字列で照合します。`/usr/bin/git push …` や `bash -c '…'` のように別の形で書かれたものは止められません。**うっかりを防ぐ仕組みであり、完全な防壁ではありません。**
- ファイル読み取りの拒否は、ファイル名を指して読むコマンドが対象です。`grep -r` のように名前を指さずに読むものや、スクリプトが自分で開く読み取りは対象外です。
- `.claude/settings.json` は、書き換えるとすぐ有効になります。そのため、**設定ファイルの変更は、PR のレビューで確かめます**（`.github/CODEOWNERS` により、統括がレビューします）。
- 完全に止めるのは、GitHub 側の設定（ブランチ保護）と PR のレビュー（`.github/CODEOWNERS`）です。ブランチ保護は統括が設定します。

規則を変えたいときは統括に依頼してください。
