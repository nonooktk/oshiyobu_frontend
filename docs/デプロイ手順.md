# デプロイ手順

手元の変更を本番に反映するまでの流れと、失敗したときの戻し方です。

デプロイ先は **Azure Static Web Apps** を想定しています。ただし設計がまだ確定していないので、決まっていない点があります。そうした点には「設計の確定後に追記」と書いてあります。書かれていないことは、決まったものとして進めないでください。

## 決まっていないこと（設計の確定後に追記）

| 項目 | 今の状態 |
| --- | --- |
| デプロイ先 | Azure Static Web Apps を想定。設計の確定後に追記 |
| CI の中身と、必須にするチェック | 設計の確定後に追記 |
| プレビュー環境の作り方と URL | 設計の確定後に追記 |
| main に入ったときの自動反映の仕組み | 設計の確定後に追記 |
| 本番の URL | 設計の確定後に追記 |
| PR のマージ方法（Squash・Merge commit・Rebase のどれか） | 設計の確定後に追記。戻し方のコマンドが変わる |
| マージと承認ができる人の権限 | 設計の確定後に追記。当面は承認者（統括）が GitHub の画面で行う想定 |
| main の直接 push を GitHub 側で止める設定（ブランチ保護） | 統括が設定する。内容は決まりしだい追記 |
| デプロイ先の「前の版に戻す」操作 | 設計の確定後に追記 |

## 全体の流れ

```
ローカルで確認 → PR を出す → CI が緑 → プレビューで確認 → 承認 → main に入れる → 自動で反映 → 反映後に確認
```

順番は飛ばしません。どこかの段で止まったら、次へ進まず、止まった段の「次へ進める条件」を確かめます。

## 各段の担当と、次へ進める条件

| 段 | 誰が | やること | 次へ進める条件（出るもの） |
| --- | --- | --- | --- |
| 1. ローカルで確認 | 担当者（Claude Code と一緒に） | アプリをローカルで動かして見る。`/pre-deploy-check` を実行する | 表がすべて ○ になる。変えた画面をスマホと PC の幅で見て、崩れがない |
| 2. PR を出す | 担当者 | 作業ブランチを push して、PR を作る | PR の URL が出る。PR の本文に、ひな形の項目がすべて埋まっている |
| 3. CI が緑 | 自動（GitHub Actions） | PR のチェックが走る | PR のチェックがすべて成功になる |
| 4. プレビューで確認 | 担当者と承認者 | プレビュー環境で画面を見る | 見た人が「見て OK」と PR にコメントしている |
| 5. 承認 | 承認者（統括） | 内容を見て承認する | 「OK」「進めてください」「Aで」「同意です」のどれかが PR かチャットに残っている |
| 6. main に入れる | 承認者（GitHub の画面で PR をマージ） | PR の画面でマージを押す | PR が「Merged」になる |
| 7. 自動で反映 | 自動（GitHub Actions） | main に入ると自動で本番に反映される | 反映の実行が成功になる |
| 8. 反映後に確認 | 担当者 | 本番で、変えた画面と主要な動き 1 本を見る | 見えるべきものが見えている。「デモ用の架空データ」の表示がある |

担当者と Claude Code は **6（main に入れる）を行いません。** 7 の反映も手元からは行いません。

### 2. PR を出す

作業ブランチを push します（Claude Code が実行前に確認を取ります）。

```
git push -u origin <ブランチ名>
```

PR を作ります。ブラウザで PR の作成画面が開きます。

```
gh pr create --web
```

本文の欄にひな形（`.github/pull_request_template.md`）が入っていれば、項目を埋めます。入っていなければ、ひな形の中身を貼って埋めます。

### 3. CI が緑

PR の画面の「Checks」を見るか、次を実行します。

```
gh pr checks <PR の番号>
```

すべて成功になるまで次へ進みません。失敗したときは、エラーを**全文**貼って聞きます。CI の中身は設計の確定後に決まります。それまで CI が無いときは、そのことを承認者に伝えたうえで、次へ進めてよいか聞きます。

### 4. プレビューで確認

プレビュー環境の URL で、変えた画面を見ます。プレビューの仕組みは設計の確定後に決まります。

### 6. main に入れる

承認者が GitHub の PR の画面でマージします。担当者は押しません。Claude Code も行いません（`gh pr merge` は拒否しています）。

### 7. 自動で反映

main に入ると自動で本番に反映されます。反映の実行は GitHub の「Actions」タブで見られます。

```
gh run list --limit 5
```

### 8. 反映後に確認

1. 本番の URL を開く（URL は設計の確定後に追記）。
2. 変えた画面が想定どおりに出ているか見る。
3. 全画面に「デモ用の架空データ」の表示が出ているか見る。
4. 主要な動きを 1 本、最初から最後まで通す。どの動きを通すかは承認者が決める。
5. 結果（OK か、見えたもの）を PR にコメントする。

書き込みを伴う動きを通すときは、**テスト用のデータだけ**を使います。本物の利用者のデータは書き換えません。

## 失敗したときの戻し方

本番が壊れたら、**main を 1 つ前の状態に戻す PR を出して、同じ流れで反映します。** 強制 push はしません。

次の操作は**どんなときも行いません**。

- 強制 push（`git push --force` など）
- `git reset --hard` で main を巻き戻す
- 手元から `az` や `swa` で本番を入れ替える

### 手順

1. **止まって承認者に伝える。** いつ、どの PR を反映したか。何が壊れているか。画面の写真かエラーの**全文**。
2. **戻す PR を作る。** どちらか 1 つの方法で行う。
   - **方法 A（簡単）**: GitHub で戻したい PR（マージ済み）の画面を開き、下のほうにある「Revert」を押す。戻すための PR が自動で作られる。書き込み権限が必要。
   - **方法 B（コマンド）**: 次の順に実行する。

     ```
     git switch main
     git pull --ff-only
     git switch -c fix/revert-<PR の番号>
     git log --oneline -n 10
     ```

     戻すコミットの ID を `git log` の出力から探します。マージ方法によって戻し方が変わります（マージ方法は設計の確定後に決まります）。

     - 「Squash and merge」のとき: `git revert <コミットの ID>`
     - 「Create a merge commit」のとき（`Merge pull request #…` という行のコミット）: `git revert -m 1 <マージコミットの ID>`

     そのあと、作業ブランチを push して PR を作る（「2. PR を出す」と同じ）。
3. **戻す PR も同じ流れで進める。** CI、承認、承認者によるマージ、自動の反映、反映後の確認。本番が壊れているときは、承認者に「戻す PR を出す」と先に伝えて、優先して見てもらう。
4. **戻ったことを確かめる。** 「8. 反映後に確認」と同じ。
5. **原因を調べて直す。** 元の変更を入れ直すときは、新しいブランチで直して、新しい PR にする。

デプロイ先の「前の版に戻す」操作は設計の確定後に追記します。

## 秘匿値の扱い

- デプロイに必要な値（トークンなど）は、統括が GitHub の Actions secrets に登録します。担当者と Claude Code は、値を見ません・書きません・持ちません。キー名を足したいときは統括に依頼します。
- **秘匿値を commit・push・PR に載せてしまったとき**は、すぐに止まって統括に伝えます。載せた値は使えなくする必要があります（あとから消しても履歴に残るため）。強制 push で履歴を書き換えて消そうとしないでください。

## 付録: Claude Code に許していない操作（`.claude/settings.json`）

次の操作は設定ファイルで拒否しています。拒否の設定は許可の設定より優先されます。Claude Code で `/permissions` を実行すると、一覧を見られます。

| 種類 | 拒否している操作 | 理由 |
| --- | --- | --- |
| main への push・強制 push | `git push` のうち、引数のないもの・`origin` だけのもの・`HEAD` を指すもの・main 宛のもの・強制（`--force`、`-f`、`+`）・リモートの削除（`--delete`）・`--mirror`・`--tags` | main に直接入れない。push してよいのは `git push -u origin <作業ブランチ名>` だけ |
| 変更を消す操作 | `git reset --hard`、`git checkout -f`、`git switch -f`、`--force`、`--discard-changes`、`git clean` | 作業中の変更が戻せなくなる |
| git の別の書き方 | `git -C …`、`git -c …` | 上の拒否をすり抜けるのを防ぐ |
| マージ・デプロイ | `gh pr merge`、`gh api`、`gh workflow run`、`gh release`、`az`、`azd`、`swa`、`npx swa`、`vercel`、`netlify` | マージとデプロイは承認を得た人が決まった流れで行う |
| 秘匿値の読み取り | `.env`、`.env.*`、`*.env`（`.env.example` は読める）、`~/.ssh`、`~/.azure`、`~/.config/gh` | 秘匿値を読まない |

Windows の PowerShell で動く Claude Code にも、同じ規則を `PowerShell(...)` の形で置いています。

### この拒否でできないこと（公式ドキュメントの記載）

- コマンドの拒否は、書かれた文字列で照合します。`/usr/bin/git push …` や `bash -c '…'` のように別の形で書かれたものは止められません。**うっかりを防ぐ仕組みであり、完全な防壁ではありません。**
- ファイル読み取りの拒否は、ファイル名を指して読むコマンドが対象です。`grep -r` のように名前を指さずに読むものや、スクリプトが自分で開く読み取りは対象外です。
- `.claude/settings.json` は、書き換えるとすぐ有効になります。そのため、**設定ファイルの変更は、PR のレビューで確かめます**（`.github/CODEOWNERS` により、統括がレビューします）。
- 完全に止めるのは、GitHub 側の設定（ブランチ保護）と PR のレビュー（`.github/CODEOWNERS`）です。ブランチ保護は統括が設定します。

規則を変えたいときは統括に依頼してください。
