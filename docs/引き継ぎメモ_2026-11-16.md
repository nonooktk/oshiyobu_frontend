## 5. 作業のしかたで分かったこと

- **PR の宛先**: 事務所向け（B 側）は `dev`、ファン向け（C 側）は `feat/fan-flow-v2`。#30 は初め `main` 宛で、325 ファイルの差分に見えていた。レビューの前に宛先を見る
- **宛先を変えただけでは CI が走らない**。「Update branch」のボタンも出ない。担当者が手元で `dev` を merge して push すると走る
- **承認は GitHub の上で確かめる**。`gh pr view <番号> --json reviewDecision` が `APPROVED` になってからマージする。`--admin` での迂回は使わない
- **マージは Squash だけ**。`gh pr merge <番号> --squash --match-head-commit <SHA>` で、確かめた版だけを入れる
- **PowerShell から `gh --jq` に `"` を含む式を渡すと失敗する**。`--jq '.field'` の形で、項目ごとに分けて呼ぶ
- **手元の Node は v24.14.0**（`engines` は 24.15.0 以降）。`npm run verify` に注意が 1 件出るが、判定は合格になる
- **`.claude/settings.json` の deny は、このフォルダで起動したセッションでだけ効く**。親のフォルダで起動すると `tests/guard/` と `docs/守ること.md` が書けてしまう。この 2 つは、統括の指示があるときだけ直し、PR の本文に指示を書く（G-24）
- **配備**は、Actions の `deploy.yml` を手で起動し、環境 `production` の承認を統括が出す。対象は `main` と `dev` だけ。手元からは配備しない
