# 検収（手元の検査と、API との通信の確認）

変更を渡す前に、次の 2 つを確かめる手順です。

1. 手元の検査がすべて通ること（CI と同じ検査）。
2. 画面が API（backend）と実際に通信できていること。

この手順書は、担当者とその Claude Code が使います。要点は `CLAUDE.md` の「8. 検収のしかた」にまとまっています。ここでは、出力の読み方、落ちたときの見分け方、細かい指定を説明します。命令の実行には、bash も Python も要りません（Node だけで動きます。Python が要るのは、書体を絞り直すときだけです。`docs/フォント.md`）。Mac でも Windows でも、同じ命令を使えます。

## 1. 命令の一覧

| 命令 | 確かめること | 要るもの |
| --- | --- | --- |
| `npm run verify` | lint・型・整形・テスト・ビルド・量と絵の検査（`--strict-images`）・CSP の検査・`src/core/` が lock のとおりか。CI（`ci.yml`）が実行する検査と同じで、配備（`deploy.yml`）が実行する検査もすべて含む | `npm ci` を済ませた状態 |
| `npm run check:api` | API が決まり（契約）どおりに答えるか。`/healthz`・メーター・404・CORS・応答の時間（`--write` を付けたときだけ、申し込みの動きも） | API の接続先 |
| `npm run check:live` | 実ブラウザ（手元の Chrome）で 3 ページを開き、エラーが出ていないか、札が 2 枚あるかを確かめる。あわせて、既定（ひとり体験）では、`/fan/` が API を呼んでいないこと、`/presenter/` の「接続を確認する」で、ブラウザから API に届くこと（`--shared` では、`/fan/` からメーターの取得が届くこと） | API の接続先（手元の画面を開く場合）か、公開中の画面の URL |
| `npm run api:local` | 手元で API を起動する（`core.lock.json` が指すコミットの backend）。止めるときは `Ctrl + C` | ネットワーク（初回だけ GitHub から取得する） |
| `npm run e2e:solo` | ひとり体験の通し（実ブラウザで、はじめの画面 → 申し込む → 80% の演出 → 仲間を呼ぶ → 成立の演出 → 閉じて開き直す）。`accept` が 1 項目として回す | Chrome |
| `npm run accept` | `verify` → `check:api` → `check:live` → ひとり体験の通し（`e2e:solo`）を順に実行し、最後に項目ごとの表を出す。**検収の入口** | 上のとおり |

API の接続先が渡されていないと、`accept` は通信の 2 つ（`check:api`・`check:live`）を「飛ばした」と表示します。このとき判定は「未完了」になり、合格とは区別されます。

**ファン向けは、既定では「ひとり体験」です。** 人数を端末の中だけで数え、`VITE_API_BASE` があっても API を呼びません。API を使うのは、発表者用（`/presenter/`）の「接続を確認する」とリセットだけです。ビルド時に `VITE_SHARED_METER=on` を渡したときだけ、ファン向けが共有メーター（全員の申し込みを API で集める形）で動きます。検収も、この 2 通りで確かめ方が変わります（3 節・4 節の `--shared`）。

用語: **接続先**は、画面がつなぐ API の origin（`https://…` の形。環境変数 `VITE_API_BASE`）。**接続元**は、API から見た、画面の origin です。API は、許可した接続元からの通信にだけ、CORS の許可（`Access-Control-Allow-Origin`）を付けます。

## 2. 前提

| もの | 内容 |
| --- | --- |
| Node | `.nvmrc`（22）と `package.json` の `engines` で指定。22.22.2 以降の 22 系・24.15.0 以降の 24 系・26 以降。奇数の版（23・25）は対象外 |
| Chrome | `check:live` と `accept` が使います。インストール済みの Google Chrome でそのまま動くので、ブラウザを別にダウンロードする必要はありません |
| 依存 | 最初に一度、`npm ci` を実行する |

Node が範囲の外でも、動くことはあります。範囲外のとき `npm run verify` は「注意」を出しますが、不合格にはしません。ただし、CI（Node 22）と同じ結果になるとは限りません。範囲外で何かが落ちたら、まず Node を対象の版に入れ替えてください。Node 20 では、TypeScript のファイルを読み込むスクリプト（`check:csp` など）が動かず、テストの実行も失敗します（Node 20.20.2 で確かめました）。

## 3. 手元だけで閉じる検収（担当者の標準）

管理者から値をもらわなくても、自分の PC だけで検収を終えられます。

```
npm ci
npm run accept -- --local-api
```

`--local-api` を付けると、次の順に進みます。

1. `npm run verify` を実行します。
2. `core.lock.json` が指すコミットの backend を OS の一時フォルダに取得し、ビルドして起動します（ポート 8795）。初回は 1〜2 分かかります。2 回目からは、取得したものとビルド結果を使い回します。
3. `npm run check:api` と同じ確認をします。手元の API なので、書き込み（`--write`）も自動で付けます（試験用の公演 1 つだけに、新しい端末の番号で 2 回送ります。人数は 1 だけ増えます）。
4. 手元の API を接続先にして、画面を既定（ひとり体験）でビルドし（`dist-accept/`）、手元で配って（ポート 5295）、`npm run check:live` と同じ確認をします。
5. ひとり体験の通し（`npm run e2e:solo`）を回します。自分でビルド（`dist-solo/`）して、ポート 5297（画面）と 8798（偽の API）を使います。20 秒ほどです。
6. 最後に、手元の API と、配っている画面を、`accept` が自動で止めます。

ほかのプログラムがポートを使っているときは、`--api-port <番号>` と `--web-port <番号>` で変更します（ひとり体験の通しの 5297・8798 は変えられません。使用中なら、その項目は「飛ばした」になります）。

```
npm run accept -- --local-api --api-port 8800 --web-port 5300
```

### 共有メーターに戻した画面を確かめる（`--shared`）

共有メーター（ビルド時に `VITE_SHARED_METER=on`）の画面を検収するときだけ、`--shared` を付けます。

```
npm run accept -- --local-api --shared
```

- 手元の画面を、`VITE_SHARED_METER=on` を付けてビルドします。`check:live` は、既定の「`/fan/` が API を呼ばない」の代わりに、「`/fan/` からメーターの取得が出て 200 で返り、CORS で許される」ことを確かめます。`/presenter/` の「接続を確認する」は、どちらでも確かめます。
- ひとり体験の通し（`e2e:solo`）は、共有メーターの画面には当てはまらないので、回しません（表にも出ません）。
- 自分の環境変数の `VITE_SHARED_METER` は、手元のビルドに持ち込みません。ビルドの指定は、`--shared` の有無だけで決まります。
- 公開中の画面を確かめるときは、公開中の画面がどちらでビルドされているかを、管理者に聞いて、合わせます（共有メーターなら `--shared` を付ける。付けないと、「`/fan/` は API への通信が 0 件」が不合格になります）。`deploy.yml` は、いま `VITE_SHARED_METER` を渡していないので、公開中の画面は既定のひとり体験です。

## 4. 公開中の API・画面を確かめる（管理者が値を渡したとき）

API の接続先には、GitHub の Variable `VITE_API_BASE` と同じ値を使います。画面の公開 URL には、Secret `SWA_BASE_URL` と同じ値を使います。どちらの値も、リポジトリの管理者（統括）に聞いてください。**値は環境変数にだけ入れます。** 文書・PR・commit・ログ、チャットへの貼り付けには書かないでください。

| やること | Mac（ターミナル） | Windows（PowerShell） |
| --- | --- | --- |
| 値を入れる | `export VITE_API_BASE="<API の接続先>"`<br>`export SWA_BASE_URL="<画面の URL>"` | `$env:VITE_API_BASE = "<API の接続先>"`<br>`$env:SWA_BASE_URL = "<画面の URL>"` |
| 検収する | `npm run accept` | `npm run accept` |
| 値を消す | `unset VITE_API_BASE SWA_BASE_URL` | `Remove-Item Env:VITE_API_BASE, Env:SWA_BASE_URL` |

- **値を命令の引数（`--api …`）で渡さないでください。** npm は実行する命令を `> node scripts/…` の形で画面に表示するため、引数に渡した値がそのまま出力に残ります。環境変数で渡せば表示されません。
- `SWA_BASE_URL` を入れると、`check:live` は手元でビルドせず、公開中の画面を開きます。入れなければ、手元でビルドした画面を開きます。
- 公開中の API に `--write`（書き込み）を付けるのは、管理者から指示があったときだけにしてください。書き込み先は、発表に使わない試験用の公演（`terao:KGS-001`）に限られます。発表に使う公演（`tech0:` で始まるもの）には、スクリプトは送信しません。
- **手元の画面から公開中の API を確かめると、CORS で不合格になることがあります。** 公開中の API は、公開中の画面の接続元だけを許可する作りだからです。この組み合わせは避けて、`SWA_BASE_URL` を入れて公開中の画面を確かめるか、`--local-api` で手元の API を使ってください。

## 5. 命令ごとの指定

### npm run verify

引数も環境変数も要りません。途中で 1 つ落ちても止まらず、最後まで実行して、どれが落ちたかをまとめて表示します。ただし `build` が落ちたときは、`build` の結果を使う `check:budget` と `check:csp` を「飛ばした」と表示します。

### npm run check:api

| 指定 | 内容 |
| --- | --- |
| `VITE_API_BASE`（または `--api`） | API の接続先 |
| `--web-origin`（または環境変数 `SWA_BASE_URL`） | 画面の接続元。CORS の 3 項目で使う。無いときは、この 3 項目が「飛ばした」になる |
| `--write` | 申し込みの動きも確かめる（試験用の公演に、実行のたびに新しい端末の番号で 2 回送る。1 回目は `counted: true`、同じ番号での 2 回目は `counted: false` になり、人数は 1 だけ増える） |

`reset` は送りません（合言葉を持っていないので、送れません）。応答の時間は、目安（1000 ms）を超えると「注意」になりますが、合否には影響しません。

### npm run check:live

| 指定 | 内容 |
| --- | --- |
| `VITE_API_BASE`（または `--api`） | 手元の画面をビルドするときに使う API の接続先 |
| `SWA_BASE_URL` | 入れると、公開中の画面を開く |
| `--web-port` | 手元で配る画面のポート番号（既定 5295） |
| `--shared` | 共有メーター（`VITE_SHARED_METER=on`）でビルドした画面として確かめる（3 節）。手元の画面は、これを付けてビルドする |
| `ACCEPT_CHANNEL` | 既定は `chrome`。`chromium` にすると、Playwright 同梱のブラウザを使う（先に `npx playwright install chromium` が必要。版が合わず、起動しないことがある） |

確かめるのは `/`・`/fan/?p=4`・`/presenter/` の 3 ページです。各ページで、エラーと失敗した通信が 0 件で、札「動作確認用のデモ画面です」と「デモ用の架空データ」の 2 枚があることを見ます。既定では、`/fan/` の API への通信が 0 件であることと、`/presenter/` で「接続を確認する」を押して、`/healthz` が 200・CORS で許され、画面に「応答 N ms」が出ることを見ます。申し込みのボタンと、リセットは押しません。出力には、画面や API の URL が出ません（`<SWA>`・`<LOCAL>`・`<API>` に置き換わります）。

### npm run accept

`--local-api`・`--write`・`--api-port`・`--web-port` に加えて、次の 2 つがあります。

| 指定 | 内容 |
| --- | --- |
| `--shared` | 共有メーターの画面として確かめる（3 節）。ひとり体験の通しは回さない |
| `--skip-solo` | ひとり体験の通しを回さない。その項目は「飛ばした」になり、判定は「未完了」になる |

### npm run api:local

指定できるのは `--api-port`（既定 8795）と `--web-port`（既定 5295）です。`--web-port` は、API が許可する画面の接続元のポート番号です。合言葉は設定しないので、`reset` は使えません。データは一時フォルダに置かれ、止めると消えます。

### 終了コード

| コード | 意味 |
| --- | --- |
| 0 | すべて合格（「注意」があっても 0） |
| 1 | 不合格がある |
| 2 | 不合格は無いが、「飛ばした」項目がある（**合格ではありません**） |

## 6. 出力の読み方

結果は、1 項目 1 行の表で表示されます。

| 結果 | 意味 |
| --- | --- |
| 合格 | 確かめて、決まりどおりだった |
| 不合格 | 確かめて、決まりと違った。「次に見る場所」に、調べる先が出る |
| 飛ばした | 確かめられなかった。前提が足りない（API の接続先が無い、など） |
| 注意 | 合否には関係しない知らせ（Node の版が範囲の外、応答が遅い） |

`--local-api` で全部が通ったときの最後の部分は、次のようになります（時間と件数は実行のたびに変わります）。

```
判定: 合格（合格 25・不合格 0・飛ばした 0・注意 0）
```

不合格があるときは、表の下に「次に見る場所」と、落ちた検査の出力の末尾（20 行まで）が表示されます。出力の全文は、画面を上にさかのぼると読めます。

## 7. 落ちたとき

| 落ちた項目 | 原因 | 直す所 | 誰が |
| --- | --- | --- | --- |
| `verify` の `core:check`・テストの `core-lock` | `src/core/` を手作業で変更した | 変更した箇所を元に戻し、`git diff -- src/core` で確かめる。必要な変更は backend 側で行う | 戻すのは担当者。backend と `core:sync` は管理者 |
| テストの `fonts` | 画面に新しい字を足した（書体の字の漏れ） | `docs/フォント.md` の「5. 画面の字を足したとき」を見る。絞り直しには Python と元のフォントが必要。元のフォントが無ければ、漏れた字の一覧を添えて管理者に伝える | 担当者（元のフォントは管理者から） |
| テストの `type-scale` | `font-size` に px を直接書いた | `src/styles/tokens.css` の文字の大きさの段のトークン（`--fs-*`）を使う（`docs/フォント.md` の「2.」） | 担当者 |

| `check:api` の「申し込み」（`--write`） | 申し込みの動きが決まりと違う | API の版を確かめ、管理者に連絡する | 管理者 |
| `check:live` の各ページ（コンソールのエラー） | エラーの文言で見分ける。CSP の違反なら、外部の読み込みを足している。CORS なら、接続元が違う | CSP の違反なら、足した外部の読み込みを外す。CORS なら、接続元を管理者に確かめる | 前者は担当者、後者は管理者 |
| `check:live` の各ページ（失敗した通信） | 404 なら、存在しないファイルを読み込んでいる | 参照を直す | 担当者 |
| `check:live` の各ページ（札が無い） | 札 2 枚のどちらかを消した・文言を変えた | `DemoBadge` を戻す | 担当者 |

| `accept` の「ひとり体験の通し」 | 通しのどこかが落ちている（はじめの画面・申し込む・80% の演出・仲間を呼ぶ・成立の演出・開き直し）。ファン向けの画面・文言の変更が原因のことが多い | 出力の末尾の落ちた手順と、画面写真（`test-results/solo`）を見る。`e2e-solo/solo.spec.ts` の期待値は、勝手に変えない | 担当者（期待値の変更は、先に相談） |
| `accept` の「ひとり体験の通し」が「飛ばした」 | ポート 5297・8798 が、ほかのプロセスで使用中 | 使っているものを確かめる（自分が起動したものだけを止める）。または `--skip-solo` | 担当者 |
| `check:live --shared` の「メーターの取得」 | 取得の通信が出ていない／200 でない／CORS で許可されていない。多くは、`VITE_API_BASE` がビルドに入っていない・`check:csp` が落ちている・API が止まっている・接続元が違う、のどれか | `check:csp` を先に直す。API と接続元は、管理者に確かめる | 原因による |
| `check:live` の「ブラウザ（Chrome）の起動」 | Chrome がインストールされていない | Google Chrome をインストールする | 担当者 |

## 8. 合格でわかること・わからないこと

**わかること**

- 手元の変更が、CI・配備と同じ検査を通ること。
- API が、画面が取り込んでいる core と同じ版で動き、メーターの契約どおりに答えること。
- 実ブラウザの画面が、CSP と CORS を通り抜けて、API に届くこと（既定は、発表者用の「接続を確認する」の `/healthz`。`--shared` は、ファン向けのメーターの取得）。
- 既定のファン向けが、API を呼ばない（ひとり体験の決まり）こと。ひとり体験の通しが、実ブラウザで最後まで動くこと。

**わからないこと**

- 本番での速さや、大勢が同時に使うときの動き（負荷試験は別で、backend の `loadtest/` で行う）。
- Chrome 以外のブラウザ、実機のスマホ、画面の見た目の良し悪し。
- セキュリティの専門的な点検（認証・認可・脆弱性の監査）。

**この作りは、デモ用に限ります。** 次の点は、本番（実際の金銭・個人を扱う使い方）には向きません。本番で使うなら、作り直す必要があります。

- API の接続先が、公開される JS と、配信の設定（CSP の `connect-src`）に入ります。秘密にはなりませんが、このリポジトリの文書・PR・ログには、値を書かない決まりです（4 節）。
- 申し込みを、ブラウザが作る端末の番号だけで数えています。ログインも本人確認も無いため、番号を作り直せば人数を増やせます。

## 9. その他

- 手元で作るもの: `dist-accept/`（手元の画面のビルド結果。git の管理外）と、OS の一時フォルダにある `oshiyobu-accept-backend`（取得した backend。消してかまいません。次の実行で作り直されます）。
- Windows でも、命令は同じです。ただし、これらのスクリプトは Mac で作り、Mac で確かめています。Windows で動かないときは、エラーの全文を貼って、管理者に伝えてください。
- 手元でサーバーを起動したときは、**自分が起動したプロセスだけ**を、PID を指定して止めます（Mac: `kill <PID>`、PowerShell: `Stop-Process -Id <PID>`）。`pkill`・`killall` や、ポート番号だけを指定した一括の停止は使わないでください。ほかの人のサーバーまで止めてしまうおそれがあるためです。`accept` と `check:live` は、起動したサーバーを自動で止めます。
- 検収の中身（`VERIFY_STEPS`）は `scripts/accept-lib.mjs` の 1 か所にだけ定義されています。CI も `npm run verify` を呼び出すため、手元と CI で検査の内容がずれることはありません。
